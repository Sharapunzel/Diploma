# Защищённая Kafka

Kafka 4.2.0 запускается с SCRAM-SHA-512 и `StandardAuthorizer`. Любой клиентский listener требует аутентификации, отсутствие ACL означает отказ. Controller listener слушает только loopback внутри контейнера Kafka и недоступен другим сервисам Compose; через Nginx Kafka не проходит. Топики по прежнему могут создаваться брокером автоматически, но runtime reader не получает `Create`.

## Служебные права

| Principal | Назначение | Права |
| --- | --- | --- |
| `diploma-kafka-admin` | Начальная настройка SCRAM, ACL и обслуживание брокера | Kafka superuser; секрет доступен только брокеру и одноразовому `kafka-acls` |
| `diploma-reader` | Metadata, проверка подключения, debug snapshot и consumer приложения | `Describe`, `Read` для всех топиков; `Read` для групп с префиксом `diploma-source-` и `diploma-debug-isolated` |

Широкое чтение топиков нужно существующему UI для обнаружения произвольных топиков до регистрации источника. Оно не даёт запись, создание, удаление, изменение ACL или SCRAM credentials. Для внутреннего обмена единственного совмещённого broker/controller также указан `User:ANONYMOUS` в `super.users`; он применим только к controller listener на loopback контейнера, поскольку оба доступных клиентских listener требуют SASL. Тестовые principals для проверки ACL не входят в конфигурацию. Provisioning агентов пока остаётся за изолированным admin-контуром; отдельный интерфейс, пользователи и права агентов появятся в TASK-20. Секрет администратора не монтируется в API и не передаётся через HTTP.

## Локальная разработка

Из корня проекта выполните `python scripts/prepare_dev_kafka.py`, затем `docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d`. Скрипт однократно создаёт два случайных тестовых пароля в неотслеживаемой `.dev/` и не перезаписывает их. Не используйте эти credentials в удалённом стенде или production. Внешний listener привязан к `127.0.0.1`, внутренний доступен только в сети Compose. Оба используют `SASL_PLAINTEXT` с SCRAM и ACL. Если задать `KAFKA_BIND_ADDRESS` вне `127.0.0.1`/`::1`, брокер откажет в запуске. Для удалённой разработки используйте TLS-профиль production с тестовыми, но отдельными секретами.

Работающий backend требует полного серверного Kafka-профиля и прекращает запуск, если он отсутствует. `SASL_PLAINTEXT` разрешён для точных адресов из `KAFKA_DEV_ALLOWED_BOOTSTRAP_SERVERS`: loopback-хосты и `kafka:9092` в Compose. Список можно настроить для локального host-порта; произвольное имя, соседний loopback IP и удалённый адрес будут отклонены. Удалённый dev использует `SASL_SSL`.

В UI создавайте Kafka-подключение с внутренним адресом `kafka:9092`. Логин, пароль, механизм SASL и CA задаёт серверный профиль; пользователь их не выбирает. Старое поле `security_protocol` принимается от совместимых клиентов только со значением `PLAINTEXT`, но отсутствует в OpenAPI и ответах; сохранённая колонка БД остаётся legacy-метаданными и не управляет транспортом. Каждый адрес в `bootstrap_servers` должен быть доступен от backend; все адреса, которые Kafka возвращает через `advertised.listeners`, также должны разрешаться и соответствовать TLS сертификату.

## Production

На Linux-хосте подготовьте вне Git отдельные файлы `KAFKA_ADMIN_PASSWORD_FILE`, `KAFKA_READER_PASSWORD_FILE`, `KAFKA_BROKER_PEM_FILE` и `KAFKA_CA_FILE`. Для двух паролей используйте длинные независимые случайные строки. PEM брокера содержит незашифрованный приватный ключ и цепочку сертификатов; CA-файл содержит доверенный корень. Сертификат должен иметь SAN для `kafka` и внешнего адреса `KAFKA_PUBLIC_HOST`; задайте внешний порт `KAFKA_HOST_PORT` равным опубликованному Compose порту. Внутренний и внешний listener используют `SASL_SSL`; клиенты проверяют цепочку и имя хоста. При отдельном сертификате для внутренних и внешних адресов потребуется явная дополнительная конфигурация listener.

Файлы паролей и ключа должны быть читаемы только назначенными UID контейнеров (Kafka: 1000, API: 10001 для reader и CA), а родительские каталоги — доступны им для прохода. Укажите пути в закрытом `.env.production` на Linux-хосте вместе с остальными переменными из корневого README. В Compose переменные содержат только пути к секретам, а не пароли или ключ. Перед `up` проверьте `docker compose --env-file .env.production -f docker-compose.yml -f docker-compose.prod.yml config`: адреса, порты, имя проекта и тома. Не публикуйте вывод, если в других переменных есть секреты. После `up` дождитесь успешного `kafka-acls`; API запускается только после него.

Для прямого запуска backend без Compose задайте `KAFKA_SECURITY_PROTOCOL=SASL_SSL`, `KAFKA_RUNTIME_USERNAME=diploma-reader`, `KAFKA_RUNTIME_PASSWORD_FILE` и `KAFKA_CA_FILE` с локальными защищёнными путями. Production откажет в старте, если профиль не `SASL_SSL`. Ошибка TLS, SCRAM или ACL не приводит к откату на незащищённое соединение.

## Переход существующего Kafka volume

Переход требует короткой остановки Kafka. Не запускайте `docker compose down -v`, `kafka-storage format` или пересоздание тома. Зафиксируйте до перехода имена и ID топиков, наличие сообщений и подтверждённые offsets нужных групп; сделайте штатную резервную копию тома в остановленном состоянии. Сначала подготовьте защищённые файлы паролей и, для production, сертификат с SAN для `kafka` и внешнего адреса и доверенный CA.

1. Пока старый broker ещё работает, установите зависимости backend и выполните `python scripts/seed_kafka_scram.py --bootstrap <старый-host:port> --protocol PLAINTEXT --admin-password-file <путь> --reader-password-file <путь>` для строго локального dev. Для старого production listener укажите `--protocol SSL --ca-file <путь>`. Скрипт читает пароли из файлов и отправляет запрос Kafka Admin API, не помещая их в аргументы процесса. Запуск повторяем; старый PLAINTEXT listener не проверяет новые SCRAM credentials.
2. Остановите API и старый Kafka, сохранив именованный том. Проверьте, что новый Compose-проект указывает **на тот же** Kafka volume и прежний `CLUSTER_ID`. Не меняйте project name случайно: иначе Compose создаст пустой новый том.
3. Запустите защищённые `kafka` и `kafka-acls`, дождитесь `healthy` и успешного завершения ACL bootstrap. Затем запускайте API и остальные сервисы. Новый entrypoint обнаруживает `meta.properties` и не форматирует существующее хранилище.
4. На защищённом listener проверьте вход admin и runtime reader; затем под runtime reader проверьте тот же cluster/topic ID, сообщение, group offset, metadata и чтение приложения. При проблеме остановите новые контейнеры **без удаления тома** и верните прежний Compose-конфиг/listener. Добавленные SCRAM credentials и ACL останутся в Kafka metadata, но старый клиентский путь продолжит работать; после исправления причины повторите переключение. Не сбрасывайте consumer offsets.

Если bootstrap ACL завершился ошибкой, API не запускается. Не обходите этот отказ запуском старого анонимного listener. Диагностику проводите по состоянию контейнеров и категориям ошибки Kafka: недоступность сети, проверка TLS/имени, SCRAM credentials, отказ ACL. Пароли, полный JAAS config и приватные ключи не копируйте в логи и отчёты.

Текущий один узел Kafka не даёт высокой доступности. Автоматическая ротация секретов, отдельные агентские учётные записи, их ACL и конфигурации Fluent Bit не входят в TASK-19.
