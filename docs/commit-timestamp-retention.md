## Повторяемая проверка

Из корня проекта, с зависимостями backend и доступным Docker:

```powershell
python -B scripts/check_commit_timestamp_retention.py
```

Сценарий использует `prepare`, `check_config`, инвентаризацию и сравнение ресурсов
из единого `scripts/agent_test_profiles.py`, профиль `backend-db`, существующие
development Compose-файлы и образ `postgres:18`. Он запускает только PostgreSQL
в уникальном Compose-проекте, с отдельным томом и свободным loopback-портом.
Тестовое переопределение включает `track_commit_timestamp` до первой записи.
Рабочие БД и секреты не используются. Все файлы находятся в единственном
`.test_runs/runs/commit-retention-<uuid>/`; TEMP/TMP/TMPDIR указывают туда.
В `finally` удаляются ресурсы проекта и каталог, проверяется Docker-инвентарь,
включая образы и build cache. Сборок и загрузки новых образов не требуется при
наличии проектного PostgreSQL 18. При ошибке очистки каталог сохраняется для
диагностики; путь выводится в traceback.

Код 0 означает **подтверждённый контрпример**, а не прохождение gate.

Проверяются:

1. Реальный INSERT с завершением транзакции и сохранённым `writer_xid`.
2. Наличие `pg_xact_commit_timestamp(writer_xid)` после commit.
3. Контрольная ранняя материализация метки в обычный `timestamptz`.
4. Продвижение горизонта XID через `VACUUM FREEZE` всех БД изолированного
   кластера, включая временное разрешение соединений с его `template0`.
5. Перезапуск PostgreSQL: исходная запись и материализованный контроль
   сохраняются, исходная метка commit по прежнему XID уже возвращает `NULL`.

Это ускоренное воспроизведение утраты метаданных при продвижении горизонта,
а не измерение времени хранения в днях и не утверждение, что любой одиночный
VACUUM немедленно удаляет все метки. Пауза материализатора сама по себе не
продвигает XID; риск возникает при продолжающейся активности кластера и vacuum.

## Почему раннего фонового UPDATE недостаточно

Материализация уже полученной метки надёжна, что подтверждает контроль.
Однако между commit INSERT и commit материализации существует интервал сбоя:
процесс может завершиться сразу после INSERT. При долгом простое оставшиеся
метаданные могут быть удалены. Сохранение отдельного XID и блокировка источника
не удерживают историю commit timestamp. Метку невозможно прочитать внутри
ещё не завершённой транзакции её собственного INSERT. Синхронный вызов после
commit уменьшает интервал, но не устраняет его при аварии.

Документация PostgreSQL прямо указывает удаление commit timestamp при vacuum:
[Committed Transaction Information Functions](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-COMMIT-TIMESTAMP).
Горизонт хранения связан с возрастом транзакций, а не с гарантированным сроком:
[Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html).
Повышение freeze-порогов лишь отодвигает проблему и не доказывает сохранность
при произвольном простое. Отключение защитного vacuum не является решением.

## Передача Этапному архитектору

Нужно блокирующее решение до реализации зависимой временной основы:

- Сохранить требование фактического commit: исследовать захват commit из WAL
  с удержанием необходимых данных до подтверждённой материализации. Потребуются
  проверка crash recovery, дискового бюджета, поведения при потере WAL/слота
  и барьера закрытия окна. Это кандидат на новый механизм, не принятое решение
  и не доказанная реализация.
- Ограничить допустимый простой/возраст XID и определить управляемый отказ
  и восстановление при утрате меток. Такой вариант не выполняет текущую гарантию
  восстановления; его допустимость требует явного согласования.
- Пересмотреть смысл времени принадлежности событию. Это меняет согласованный
  контракт фактического commit и требует решения человека с Главным архитектором.

Подставлять `backend_processed_at`, время начала транзакции или время
последующей материализации в рабочий `availability_at` нельзя. Правильный
безопасный отказ при `NULL` предотвращает ошибочную классификацию, но не
восстанавливает пропущенные рабочие окна и не завершает TASK-30.

Миграции, consumer, Compose приложения и числовые расчёты не менялись:
их реализация до выбора механизма создала бы зависимую переделку.
Полные backend/Kafka-наборы, production и frontend не запускались: приложение
не изменено; выполнена только изолированная диагностика retention gate.
Проверка обоих режимов и все критерии TASK-30 остаются обязательными после
устранения блокирующего ограничения.
