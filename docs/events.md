## Обработанные логи и каталог ECS

API поставляет generated artifact Elastic Common Schema из неизменяемого
[релиза `v9.4.0`](https://github.com/elastic/ecs/tree/v9.4.0). Исходный YAML,
лицензия автора, дата получения, URL источника и SHA-256 находятся в
`app/resources/ecs/`. Каталог загружается локально, без сети; позже тот же API каталога
можно использовать для подсказок и валидации полей нормализатора. Источник —
`generated/ecs/ecs_flat.yml` с тегом `v9.4.0` (`ecs_flat_v9.4.0.yml` в репозитории),
получен 2026-09-23; SHA-256:
`f2c78b7c68503d42f5713ebea63fbfafbbeb7056f0d3ec7208c9cc2202ba7d8f`.

Все перечисленные endpoints требуют аутентифицированную сессию. Каталог, поиск и карточка
требуют `events.read`; удаление одного или нескольких событий — `events.delete`. Каждый
POST (включая поиск только для чтения) и DELETE передаёт привязанный к сессии токен в
`X-CSRF-Token`, полученный из `GET /api/v1/auth/session`.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/ecs/schema` | Версия ECS, число полей и сведения о происхождении артефакта |
| `GET /api/v1/ecs/fields?q=&type=&level=&filterable=&limit=50&offset=0` | Поиск и просмотр отсортированного каталога |
| `GET /api/v1/ecs/fields/{field_name}` | Одно поле ECS, включая `@timestamp` |
| `POST /api/v1/parsed-logs/search` | Поиск нормализованных логов |
| `GET /api/v1/parsed-logs/{log_id}` | Полные сырые данные и ECS одного события |
| `DELETE /api/v1/parsed-logs/{log_id}` | Удаление одного события |
| `POST /api/v1/parsed-logs/actions/delete` | Удаление по источнику, интервалу времени или обоим условиям |

Поиск сочетает группы ID, топиков и разделов (OR внутри группы, AND между группами),
полуоткрытые временные границы `[from,to)`, буквальный поиск подстроки сырого лога и до
20 фильтров полей ECS. `%`, `_` и обратная косая черта в `raw_query` считаются буквальными.
Пример:

```json
{
  "raw_query": "authentication failure",
  "processed_from": "2026-01-01T00:00:00Z",
  "processed_to": "2026-02-01T00:00:00Z",
  "ecs_filters": [
    {"field": "event.action", "operator": "eq", "value": "login"},
    {"field": "source.ip", "operator": "eq", "value": "192.0.2.10"}
  ],
  "limit": 50,
  "cursor": null
}
```

Доступные операторы ECS публикуются вместе с полем. Строковые поля поддерживают `eq`, `neq`,
`contains` (подстрока без учёта регистра), `exists`, `not_exists`; числа — равенство и сравнение
порядка; даты — равенство и сравнение порядка с учётом часового пояса; булевы значения и
IP-адреса — равенство. Листовые поля, допускающие массив, дополнительно поддерживают
`contains`; для любого массива `eq` проверяет точное типизированное вхождение, а `neq`
требует существующий массив без указанного элемента. Для строкового массива `contains`
ищет подстроку без учёта регистра внутри элементов; для чисел, булевых значений, дат и IP
проверяет типизированное вхождение. Неверные IP и даты отклоняются всеми операторами;
целочисленные ECS-поля принимают только целые числа JSON. `exists` означает наличие пути
JSON, включая явный `null`; `not_exists` — отсутствие пути. Повреждённые сохранённые
значения не подходят под сравнения `eq`, `neq`, `contains`. Неподдерживаемые и объектные
типы ECS остаются в каталоге, но не фильтруются. Имена полей проверяются по доверенному
каталогу до построения параметризованного запроса JSONB; клиент не передаёт SQL, casts
или пути JSON.

Результаты упорядочены по `backend_processed_at DESC, id DESC`. Первая страница фиксирует
границу `created_at` по времени БД; продолжения используют ту же границу. Это исключает
обычные последующие вставки и позднюю загрузку с более новым `created_at`, но не создаёт
строгий снимок БД: транзакция, завершившаяся позже с `created_at` до границы, может появиться
на следующей странице, а удаление между запросами может убрать строки. Подписанный непрозрачный
cursor содержит границу и позицию сортировки, привязанные к отпечатку нормализованных фильтров
(но не к размеру страницы). Смена фильтров, подмена cursor и повреждённый/старый формат дают
`422 invalid_cursor`. Новый поиск получает новую границу. Ответ содержит `items`, `has_more`,
`next_cursor`, без затратного общего счётчика. Краткая запись содержит не больше 500 символов
сырого текста и версию ECS, но не полные raw-данные, ECS-объект или ключ дедупликации.
Полная карточка события возвращает эти поля.

Удаление одного события возвращает `204` или `404 parsed_log_not_found`. Массовое удаление
требует UUID источника или полный непустой диапазон `[processed_from,processed_to)`;
поддерживаются только источник, диапазон и их пересечение. Пустое/глобальное удаление
отклоняется с `422 deletion_scope_required`. Массовое удаление выполняется одним запросом
в одной транзакции. Миграция `0003` устанавливает `pg_trgm`, заполняет неизменяемые снимки
имён нормализаторов (`legacy-unknown` только если прежняя связь не даёт имя) и добавляет
GIN trigram index для поиска подстроки сырого лога. Применяйте её обычной командой
`python -m alembic upgrade head`.

## API запросов событий одного источника

Общее API чтения работает с одним источником за запрос. Локальные Kafka-источники читают
документ PostgreSQL `parsed_logs.ecs_data`; внешние источники возвращают
`501 event_source_unavailable` до реализации адаптера OpenSearch в TASK-12. Отсутствующий
или удалённый источник даёт `404 source_not_found`. Существующие локальные события
читаются и после выключения Kafka-источника. Прежний API `/parsed-logs/*` сохраняет контракт
запроса и ответа.

* `GET /api/v1/events/sources/{source_id}/fields?q=source.ip&limit=50&offset=0` выдаёт
  пригодные для поиска поля ECS 9.4.0 из поставляемого каталога без сканирования событий.
* `POST /api/v1/events/sources/{source_id}/search` фильтрует одно поле на условие; условия
  соединяются AND, оператор `in` работает как OR внутри одного поля. Сортировка по
  `@timestamp`; границы времени полуоткрытые и учитывают часовой пояс. Отсутствующее или
  повреждённое историческое время исключается.
* `GET /api/v1/events/sources/{source_id}/events/{event_id}` выдаёт поля события и
  типизированное дополнение для источника. Общая карточка не требует сырой лог и метаданные
  Kafka; их выдаёт локальный вариант. ID событий — непрозрачные строки провайдера,
  действительные только для своего источника.

Пример поискового запроса:

```json
{
  "timestamp_from": "2026-01-01T00:00:00Z",
  "timestamp_to": "2026-02-01T00:00:00Z",
  "sort": "desc",
  "filters": [
    {"field": "event.action", "operator": "in", "value": ["login", "logout"]},
    {"field": "source.ip", "operator": "eq", "value": "192.0.2.10"}
  ],
  "limit": 50,
  "cursor": null
}
```

Строковые сравнения чувствительны к регистру и буквальны: `contains`, `starts_with` и
`ends_with` экранируют специальные символы SQL LIKE. Поддерживаемые операторы указаны у
каждого поля каталога. Допускается до 20 фильтров, до 20 значений `in`, до 512 символов
строкового значения, до 100 записей на странице и до 4096 символов cursor. Типы значений
проверяются до параметризованных запросов JSONB; клиент не отправляет SQL, JSONPath или
OpenSearch DSL. Повреждённые или неверно типизированные сохранённые значения не совпадают
со сравнениями. API не сканирует все документы ради обнаружения полей и не считает общее
число событий.

Для поля JSON `exists` истинен при наличии ключа, даже если значение — JSON `null`;
`not_exists` истинен только при отсутствии ключа. JSON `null` не является допустимым
типизированным значением сравнения и не совпадает ни с `eq`, ни с `neq`. Пустая строка
существует и является допустимым строковым значением: совпадает с `eq` для `""`, а `neq`
сравнивает её обычным образом.

Регистрация провайдеров по типу источника скрыта за прежними router и DTO запросов.
Каждый провайдер предоставляет собственный каталог полей поиска, ID событий и состояние
продолжения; общий протокол требует привязать cursor к источнику, фильтрам, временному
интервалу, направлению сортировки и устойчивой границе снимка провайдера. PostgreSQL
использует зашифрованный подписанный cursor с границей `created_at` по времени БД и
последней позицией `(время события, UUID)`. Обычные вставки после границы исключены;
как и в прежнем API поиска, это не долговременный снимок MVCC: поздние commit с более
ранним `created_at` могут появиться, а удаления — убрать строки между страницами.
Фильтрация JSONB и преобразование времени выполняются в PostgreSQL. Существующий GIN
index на `ecs_data` поддерживает условия вложения; для произвольного сочетания полей,
диапазонов и преобразований времени постоянное время работы не гарантируется.

```http
DELETE /api/v1/parsed-logs/7ca4e014-175a-4bfe-8e3f-5de190868647
X-CSRF-Token: <session csrf token>
```

```http
POST /api/v1/parsed-logs/actions/delete
X-CSRF-Token: <session csrf token>
Content-Type: application/json

{"source_id":"7ca4e014-175a-4bfe-8e3f-5de190868647"}
```

```json
{
  "source_id": null,
  "processed_from": "2026-01-01T00:00:00Z",
  "processed_to": "2026-02-01T00:00:00Z"
}
```

## JSON-нормализация (TASK-6)

Миграция `0004` сохраняет прежний произвольный текст как
`{"format_version":0,"legacy_rule_text":"..."}`. Такой normalizer доступен для
чтения и редактирования, но новые активации источника с ним получают
`409 normalizer_legacy_incompatible`. PATCH описания не делает правило
исполняемым: администратор должен заменить `rule` валидным объектом v1.
Downgrade восстанавливает исходный текст legacy-правила, а v1 — как JSON-текст.
Миграция не меняет `sources.is_enabled`.

`GET /api/v1/normalizers/block-types` публикует режимы и параметры блоков
(`normalizers.read`). `GET /api/v1/ecs/fields` и detail существующего каталога
дают `mappable` и `mappable_reason`; поиск и пагинация сохраняются, можно
передать `mappable=true`. `filterable` относится только к поиску событий и не
подменяет `mappable`. `POST /api/v1/normalizers/preview` (`normalizers.write`,
session-bound CSRF) принимает несохранённые `rule` и `sample`, не меняя БД:

```json
{
  "rule": {
    "format_version": 1,
    "variants": [{
      "key": "web", "priority": 10,
      "when": {"kind": "prefix", "value": "2025-"},
      "blocks": [
        {"key": "columns", "kind": "columns", "candidates": [{
          "delimiter": " ", "columns": ["date", "time", "ip", "status"]
        }]},
        {"key": "source_ip", "kind": "map_ecs", "target": "source.ip",
         "source": {"ref": "columns.ip"}, "required": true},
        {"key": "http_status", "kind": "map_ecs", "target": "http.response.status_code",
         "source": {"ref": "columns.status"}, "required": true},
        {"key": "event_time", "kind": "map_ecs", "target": "@timestamp",
         "source": {"refs": ["columns.date", "columns.time"], "join": " "},
         "transform": {"date_format": "%Y-%m-%d %H:%M:%S", "timezone": "UTC"},
         "required": true}
      ]
    }]
  },
  "sample": {"timestamp": "2025-06-01T12:01:00Z", "log": "2025-06-01 12:00:00 192.0.2.9 404"}
}
```

Варианты сортируются по уникальному числовому `priority`; первый совпавший
`when` (`prefix`, `contains`, RE2 `regex`) исполняется без перехода к следующему
при ошибке. Блоки идут по порядку массива. `regex` использует RE2 именованные
группы, `template` — литералы и `%{name}`, `columns` — ручной порядок колонок,
`json` — разрешённые dotted paths с альтернативами `requires`/`extract`.
Каждый extractor может иметь до 8 кандидатов, первый подходящий выигрывает;
`set` задаёт константные выходы кандидата. У `map_ecs` источник — `ref`,
`literal` или `refs` с `join`/`as_array`. Ключи блоков стабильны и применяются
для ссылок и диагностики, например `columns.ip`. Вложенный разбор выглядит так:

```json
[
  {"key":"outer","kind":"regex","candidates":[{"pattern":"payload=(?P<body>\\{.*\\})"}]},
  {"key":"inner","kind":"json","input":"outer.body","candidates":[
    {"requires":["event.action"],"extract":{"action":"event.action"}},
    {"requires":["action"],"extract":{"action":"action"}}
  ]},
  {"key":"action","kind":"map_ecs","target":"event.action",
   "source":{"ref":"inner.action"},"required":true}
]
```

Результат содержит `status` (`complete`/`partial`/`failed`), `variant_key`,
`diagnostics`, компактный `trace` и отдельный `fluent_bit_collected_at`.
`ecs_data` выдаётся только при `complete`/`partial`; `event.original` и
`ecs.version` задаёт система. Если событие не содержит времени и
`@timestamp` не объявлен обязательным, используется время сбора Fluent Bit,
статус `partial` с `event_time_fallback`. Обязательное невалидное время даёт
`failed`. Текущие лимиты: правило и `log` по 64 KiB, вложенность JSON 16,
варианты 16, блоки/вариант 32, кандидаты/блок 8, паттерн 1024 символа,
кэш компиляции 128 записей. Неизвестные параметры и поля, небезопасный для RE2
синтаксис, битые/будущие ссылки и несовместимые типы отвергаются до сохранения
с адресом варианта/блока/параметра. Движок не читает Kafka; следующий внутренний
сервис передаёт ему проверенный конверт и отвечает за транзакционное хранение.

## Надёжная запись результата (TASK-7)

`DurableProcessingService` обрабатывает ровно одну запись, переданную внутренним
вызовом с идентификатором источника, координатами `(connection_id, topic, partition,
offset)`, исходным payload в байтах и временем получения бэкендом. Kafka consumer,
сетевое чтение и подтверждение offset здесь отсутствуют; публичного HTTP endpoint для
создания событий или ошибок нет.

Успешная нормализация сохраняется в `logs.parsed_logs` со статусом `complete` или
`partial`; у частичного результата доступны адресные `normalization_diagnostics`.
Безвозвратно невалидные UTF-8/JSON/конверт/лог сохраняются в `logs.processing_errors`
с исходными байтами, стадией и безопасными кодами диагностики. Traceback, текст
исключений и секреты подключения в диагностический контур не записываются. Ошибка
конфигурации источника/правила либо ошибка PostgreSQL не считается обработанной
записью и должна приводить к повтору, а не к продвижению будущего Kafka offset.

`logs.processed_kafka_records` является общим durable-ledger для обоих исходов. Для
новых записей уникальный ключ охватывает UUID подключения, Kafka topic ID, partition и offset; тот же
набор координат возвращает `already_processed`, в том числе после удаления
`parsed_logs` через существующий API и после удаления конфигурационных сущностей.
Результат, строка ledger и соответствующая запись события либо ошибки фиксируются одной
транзакцией PostgreSQL. Поэтому будущий consumer может считать `stored_complete`,
`stored_partial`, `stored_failed` и `already_processed` пригодными для commit только
после возврата сервиса; сам commit выполняется вне этой границы.

Миграция `0005` добавляет статусы и диагностику событий; исторические строки получают
`complete` и пустой список причин, поскольку более точная классификация для них
недоступна. Автоматический replay учтённых ошибок не выполняется. Политики retention
и смены поколения топика описаны в разделе Kafka consumers выше.
