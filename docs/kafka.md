## Подключения и источники Kafka

Управление Kafka доступно под `/api/v1` и использует существующие пары разрешений
`connections.read`/`connections.write` и `sources.read`/`sources.write`. API принимает
только подключения `PLAINTEXT`; учётные данные, URL, произвольные параметры Kafka и секреты
отклоняются. Запросы метаданных используют `KAFKA_METADATA_TIMEOUT_SECONDS` (1–30 секунд).

Обычный порядок работы:

1. Создайте подключение с одним или несколькими проверенными bootstrap-адресами `host:port`.
2. Вызовите `POST /api/v1/kafka-connections/{id}/test` и при необходимости получите топики через
   `GET /api/v1/kafka-connections/{id}/topics`.
3. Создайте выключенный источник для существующего топика.
4. Назначьте нормализатор через `PUT /api/v1/sources/{id}/normalizer`, затем включите источник.
5. Выключите или удалите источник, когда он больше не нужен.

Создание и включение источника проверяют метаданные брокера. Список скрывает внутренние
топики с префиксом `__`, кроме случая `include_internal=true`; само чтение списка не создаёт
источник и не запускает Kafka consumer. Удаление подключения каскадно удаляет его источники,
сохраняя обработанные логи с обнулёнными внешними ключами.

## Потребители Kafka и надёжное подтверждение offsets (TASK-8)

В обычном процессе приложения для разработки или production каждый включённый Kafka-источник
работает под надзором фонового супервизора. Он замечает включение, выключение и удаление
источников без перезапуска; тестовые приложения API (`ENVIRONMENT=test`) не запускают workers,
если явно не задано `create_app(..., start_consumers=True)`. Поведение задают ограниченные настройки:

```dotenv
KAFKA_CONSUMERS_ENABLED=true
KAFKA_METADATA_TIMEOUT_SECONDS=5
KAFKA_CONSUMER_POLL_TIMEOUT_SECONDS=1
KAFKA_CONSUMER_RETRY_DELAY_SECONDS=2
KAFKA_SUPERVISOR_SYNC_SECONDS=1
```

Каждый источник имеет постоянную группу Kafka consumer `diploma-source-<source UUID>`.
Автоматическое подтверждение и сохранение offset отключены. Если у раздела нет
подтверждённой позиции и истории надёжной записи, worker явно начинает с самого раннего
доступного offset. Kafka commit всегда сохраняет *следующий* offset: после обработки `N`
подтверждается `N + 1`, только когда сервис TASK-7 вернул `stored_complete`, `stored_partial`,
`stored_failed` или `already_processed` после фиксации транзакции PostgreSQL. Consumer ждёт
callback подтверждения не дольше `KAFKA_METADATA_TIMEOUT_SECONDS`; при timeout позиция
не продвигается, а повторная доставка безопасна благодаря журналу обработки.

Неверный UTF-8, повреждённый конверт, пустое значение и Kafka tombstone — сохраняемые ошибки:
их offset можно подтвердить, не останавливая источник. Ошибки БД, правила, конфигурации и Kafka
не подтверждаются; затронутый раздел приостанавливается и повторяется, другие источники
продолжают работу. Если PostgreSQL записал результат, а Kafka commit не удался, повтор
получит `already_processed` из журнала до новой попытки подтверждения. Worker повторно
проверяет topic ID брокера непосредственно перед первым и каждым повторным commit offset,
в том числе после записи в БД. Новый ID архивирует старый источник без подтверждения offset;
недоступная проверка откладывает commit. Проверка метаданных и commit — отдельные операции
брокера, не атомарная транзакция: замена топика между ними остаётся возможной. Проверка
сужает это окно, но не устраняет его.

При создании и запуске приложение записывает и сравнивает UUID топика брокера.
Подтверждённый следующий offset `N < low` для *того же проверенного topic ID* означает
разрыв нижней границы. Worker сначала фиксирует неизменяемую запись
`logs.kafka_operational_events` со снимками источника и подключения, разделом, topic ID и
недоступным полуоткрытым диапазоном `[N, low)`, затем явно назначает раздел и переходит к
`low`. Он не создаёт искусственные логи или ошибки обработки для пропущенных offsets.
Диапазон описывает недоступные позиции Kafka, а не доказанное число потерянных сообщений.
После перезапуска существующий интервал используется повторно; дальнейшее перемещение
границы добавляет только непокрытое продолжение. Причину перемещения (например, retention
или административное удаление) из одного наблюдения определить нельзя. Разреженные позиции
внутри `[low, high)` не считаются таким разрывом; если повторный seek не восстанавливает
ожидаемую запись, только этот раздел останавливается с `offset_missing_within_watermarks`.
Если PostgreSQL не зафиксировал событие, позиция не продвигается, раздел повторяет попытку,
другие продолжают. `N == low` и `N == high` не разрывы. `N > high`, неизвестная подтверждённая
позиция при существующей истории, противоречивые метаданные, отсутствующий topic ID и старые
строки журнала с NULL topic ID требуют ручного разрешения без автоматического восстановления.
Неверная позиция останавливает только затронутый раздел.

Если Kafka сообщает *новый* topic ID под старым именем, worker атомарно записывает событие
`topic_recreated` и выключает/архивирует старый источник. Его исторические события доступны
для чтения, но обычный PATCH, смена нормализатора и включение не возвращают его в работу.
Список топиков помечает замену как `is_registered=false`; администратор должен явно создать
новый источник (с новым UUID и группой consumer), назначить нормализатор и включить его.
Новая регистрация также архивирует устаревший выключенный источник и записывает событие в
одной транзакции БД; ошибка оставляет старый источник текущим и ничего не создаёт. Новый
источник начинает с самой ранней доступной позиции. Уникальность и поиск журнала обработки
используют UUID подключения, topic ID, раздел и offset: повторное использование offset
другим поколением не даёт ложного `already_processed`. Исторические строки с NULL topic ID
не приписываются поколению автоматически и требуют явного разрешения.

Развёртывание предполагает один кластер Kafka. При регистрации первого источника к
подключению привязывается cluster ID, а не строка bootstrap-адреса; другое подключение к тому
же кластеру не может зарегистрировать источник (`409 cluster_connection_conflict`). Пока
у подключения остаются источники, изменение bootstrap/security настроек запрещено. Два
адреса одного кластера не позволяют запустить независимых потребителей физического топика.
Поддерживается один процесс приложения с включёнными потребителями; владение несколькими
кластерами и HA не реализовано. Миграция `0007` добавляет индексы поколений и операционные
события. Её откат отказывается удалять операционные события, архивное состояние или
поколения с конфликтующим старым ключом координат; разрешите это вручную перед откатом.

При завершении приложение просит workers закончить текущую надёжную операцию и закрыть
Kafka consumer. Workers работают в потоках без режима daemon. Если ожидание превышено,
приложение явно сообщает об ошибке завершения и сохраняет ресурсы БД доступными;
оно не сообщает об успешной остановке, пока worker может их использовать.

Жизненный цикл рассчитан на один процесс: для каждого источника запускайте ровно один
процесс API с включёнными Kafka consumers. Владение несколькими процессами и координация
HA вне этой задачи. HTTP endpoint для состояния consumer и ошибок обработки пока отсутствует.
