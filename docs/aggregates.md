# Серверные агрегаты

Агрегаты работают только с собственными ECS-источниками PostgreSQL. Сохранённые
правило, порядок признаков, источник и расписание неизменяемы. Копия возвращает
черновик для создания нового UUID. Серверное ядро RCF и его ограниченная
административная CLI описаны в [контракте детекторов](detectors.md).

## Интерфейс

С миграции `0021_event_time` сервер использует событийный контракт раздела
«Событийный серверный процесс» ниже. Описанный здесь UI TASK-39 ещё использует
прежние временные DTO; его адаптация относится к TASK-41. Нынешний интерфейс
не является готовым потребителем нового create/preview.

Раздел «Аномалии → Агрегаты» доступен с `aggregates.read`; создание и действия
требуют `aggregates.write`. Маршруты: `/aggregates`, `/aggregates/new`,
`/aggregates/{id}`. Список — таблица с размерностью вектора, источником,
длительностью и состоянием. «Фильтры» открывают отдельный черновик поиска по имени
и состоянию: отмена не меняет применённый серверный поиск; при ошибке остаются
предыдущие строки. Поиск и total относятся ко всему серверному набору.

Создание, копия и карточка состоят из трёх блоков:

1. Параметры процесса: имя, поисковый выбор собственного источника (первые 10,
   затем поиск по всему каталогу), произвольная длительность 1–604800 секунд,
   календарь с временем и явный пояс. Период равен длительности окна. Обязательные
   поля помечены звёздочкой; до их заполнения и исправления блоки признаков и
   диагностики приглушены и недоступны. Уже введённое правило при этом сохраняется.
2. Выходной вектор: единая адаптивная сетка признаков без заголовков отдельных
   групп. Слева находится название, справа — тумблер включения в выход и
   действия и работающая справка о включении в выход; ниже показаны приглушённые краткие сведения и формула без
   повторного раскрытия той же информации. Тумблер отличает выходные features
   от внутренних auxiliary. Выключение переносит определение во внутренние;
   повторное включение восстанавливает прежнюю координату, в том числе после
   визуального редактирования свойств, сохраняющего ключи и состав выхода,
   и после переключения JSON/визуального вида.
   Добавление в визуальном редакторе помещает новые ключи в конец клиентского
   списка, удаление убирает только удалённый ключ; позиции остальных, включая
   отключённые, сохраняются. У нового импортированного или скопированного
   документа нет прежних скрытых позиций. Включение внутреннего определения,
   создающее недопустимую ссылку вперёд, отклоняется до изменения правила
   с объяснением необходимости исправить порядок в JSON.
   Удаление последнего определения расширенной грамматики также отклоняется,
   если оно нарушает ранее допустимые ссылки остальных признаков. При отказе
   правило не меняется; после исправления порядка или формулы действие доступно.
   Импорт изменённого правила задаёт порядок своим массивом features. Ручной перестановки и
   кнопок изменения порядка нет; порядок массива features в JSON по-прежнему
   задаёт координаты вектора и сохраняется при чтении и копировании.
   Используемое определение нельзя удалить до исправления ссылок.
   Одна кнопка «Добавить признак» открывает модальный черновик. В его первом
   блоке выбирается тип: первичный без refs либо производный с именованными
   зависимостями и, при необходимости, собственными ECS-листьями. Модальное окно
   состоит из четырёх отделённых плиток: настройки признака (название, ключ и
   тип), входы, операции/условия и итоговая символическая формула. «Отмена»
   сохраняет прежнее правило. Ключ существующего признака защищён;
   отображаемое имя можно менять независимо.
3. Проверка и диагностика: начало одного завершённого окна из сетки расписания
   и способ отбора событий по времени. Последовательно выполняются проверка,
   пробный расчёт и создание. Длительность выбранного окна берётся из первого
   блока. Пробный расчёт не создаёт агрегат и не сохраняет точку истории.
   В рабочем режиме учитывается время доступности успешно сохранённой записи,
   которое может отличаться от времени возникновения ECS `@timestamp`.
   Корректность определения, оценка
   ресурсов, фактические значения и полнота представлены отдельными
   оформленными областями. Таблица выходов использует стиль «Подключений».
   Оценка ресурсов показана акцентными плитками «Ресурс: количество» с русскими
   названиями и точными числами только один раз: по последнему расчёту, а до него
   по последней проверке. Валидное правило не гарантирует пригодность
   модели или будущую производительность.

Визуальный режим и JSON редактируют только aggregate_rule. Используется
расширенный каталог операций; все условия, вложенные формулы, auxiliary и
aggregate-листья сохраняются. Числа проходят lossless-json 4.3.3: int64,
различие 1/1.0 и точные даты не округляются. Ошибочный JSON остаётся для
исправления. Реальное изменение входа сбрасывает проверки; поздний ответ не
подменяет новое состояние. Численные результаты внутренних узлов не выдумываются.

«Общий отбор событий» на странице действует на собственные ECS-входы всех
признаков. Индивидуальный «Отбор событий признака» задаётся в его окне настроек;
у отдельного агрегирующего входа формулы есть свой отбор. Эти условия
сочетаются через И: сначала отбираются события, затем вычисляются итоги окна
и формула. Ссылка берёт готовое значение зависимости с её собственным отбором.
Условия не являются порогом числового результата. Справка у полей открывается
кнопкой с информационной иконкой по нажатию, как в нормализаторах, и доступна
с клавиатуры. Пояснение поля не дублируется под контролом. У заголовков блоков
оставлено описание под заголовком без второй копии в иконке. Назначение
операций поясняется при выборе. Длинное окно настроек прокручивается внутри,
сохраняя заголовок и кнопки применения/отмены на экране.

Календарь показывает существующий момент в выбранном UTC/IANA-поясе (по
умолчанию пояс браузера). Его смена не изменяет расписание и не запускает
расчёт. Явный ввод новой даты использует текущий пояс; исходный пояс расписания
показывается отдельно. При DST-fold требуется выбрать один из двух моментов,
DST-gap отвергается без молчаливого сдвига. Неизменённая исходная ISO-строка
копии, включая микросекунды и смещение, остаётся точной. При выборе окна
предварительного или исторического расчёта календарь сохраняет точную долю
секунды расписания; выравнивание целых секунд и завершённость проверяет сервер.
ECS date-литералы
условий вводятся отдельно как точные JSON-строки.

После network/неоднозначного 5xx/некорректного обязательного 2xx создания
сохраняются неизменяемые body и Idempotency-Key. Автоматического повтора нет.
Редактирование не снимает неопределённый исход: явный replay отправляет прежнее
намерение. Подтверждение старого запроса не уничтожает изменённый черновик и
не выдаётся за его сохранение. Уход со страницы не откатывает серверный запрос.

Карточка доступна для чтения независимо от нового каталога.
При отказе каталога операций карточка показывает локальное объяснение и кнопку
повторной загрузки. Правило, экспорт и история остаются доступны; инструкция
для ИИ становится доступна после успешной загрузки операций.
Настройки и правило неизменяемы; изменение выполняется через копию с новым UUID и отдельным
детектором. Архивирование сохраняет модели и историю; удаление окончательно
останавливает новые расчёты и связанные детекторы, сохраняя модели и связи.
Операции с последствиями требуют подтверждения конкретной сущности.
Историческое окно выбирается календарём и рассчитывается явно: сервер проверяет
завершённость, выравнивание и доказанное основание времени. Оно не двигает
автоматическое расписание. График появляется только для подтверждённого результата
одного выбранного окна. У него явно показаны границы, пояс и шкала времени;
очистка или изменение даты скрывает прежний график и результат, в том числе при
позднем ответе старого запроса. В одном окне хранится одна точка, соединительная
линия для неё не выдумывается. Общая история отделена от выбранного окна и
загружается по три записи с серверной пагинацией. Выбор строки открывает точные
сведения именно этой записи, не меняя период графика. Строка кратко показывает
первые три значения; остальные открываются кнопкой «Ещё N признаков». Полные
точные значения, причины пропусков и счётчики корректных/некорректных входов
доступны в подробностях. Null, пропуски и неизвестная полнота не становятся нулём.

Кнопки обмена рядом с переключателем вида повторяют порядок и оформление
нормализаторов; справка расположена справа:

- «Копировать JSON» копирует текущее lossless-правило без параметров процесса,
  сохраняя auxiliary, условия, порядок и точные литералы. Ошибочный текст
  остаётся доступен для исправления и не заменяется прежним корректным AST.
- «Скачать .json» скачивает актуальный lossless-документ, включая auxiliary,
  условия и литералы. Blob URL освобождается. В карточке доступно скачивание,
  импорт — только в новом черновике/копии. Серверное сохранение не выполняется.
- «Импорт .json» локально читает UTF-8 правило до 1 MiB и подтверждаемо заменяет
  только черновик правила. Параметры процесса сохраняются. Ошибочный JSON
  можно применить как текст для исправления; ошибка чтения не заменяет ввод.
  Сырой транспортный лимит отличается от серверных 65536 байт compact canonical
  JSON; форматированное скачанное правило можно импортировать обратно.
- «Инструкция для ИИ» непосредственно копирует компактную самостоятельную
  инструкцию по функциям/семантике. Она не запрашивает каталог, события или
  текущее правило. Внешний ИИ сначала уточняет цель, полный каталог полей и
  смысл показателей, не требует сырые журналы и только потом формирует JSON.
- «Скопировать поля источника» отдельно собирает полный source field-catalog
  с единым catalog_hash, ECS-описаниями, типами и происхождением. Неполный,
  изменившийся или устаревший каталог не копируется. UUID и значения событий
  в текст не входят; unsupported-поля остаются с причиной.
Все операции копирования дают успех только после writeText; при отказе есть
выделяемый inline-текст для Ctrl+C и явная кнопка повторного копирования.
Приложение не вызывает внешнюю модель и не отправляет ей данные.

Сообщения можно закрыть, успешные уведомления дополнительно исчезают через
пять секунд. Закрытие сообщения не стирает черновик или подготовленный текст
для ручного копирования и не снимает неопределённый исход серверного запроса.

Frontend-проверки запускаются `python -B scripts/agent_test_profiles.py frontend`.
Команда `python -B scripts/agent_test_profiles.py end-to-end --aggregate-only`
также запускает `aggregates.live.spec.ts` и `aggregates.ui.spec.ts`: реальные
создание/preview/worker/история на двух источниках и моделируемые отказы,
права гостя, подтверждения, clipboard и адаптив. Синтетические пользователь,
источники и время передаются браузеру до очистки серверного сценария через
`AGGREGATE_BROWSER_CONFIG`; самостоятельно запускать live-spec против рабочей
БД не следует. Контейнеры, тома, сеть, builder/cache, временные секреты и
браузерные артефакты принадлежат единому runner и удаляются в его `finally`.

## API

Все маршруты находятся под `/api/v1/aggregates`. Администратору доступны
`aggregates.read` и `aggregates.write`; Guest эти права не получает.
POST и DELETE требуют действующей сессии и `X-CSRF-Token`.
Точные типы запросов и ответов публикуются OpenAPI в development.

GET списка принимает необязательные `q` (до 200 символов, пробелы по краям
удаляются) и `state=active|archived`. Поиск — регистронезависимая буквальная
подстрока имени по всему каталогу; `%`, `_`, обратная косая черта и кавычки
не становятся шаблоном или SQL. Удалённые записи исключаются. `total` и `items`
учитывают одинаковые фильтры, порядок — `created_at DESC, id DESC`.
Без фильтров поведение сохраняется: `limit=50`, `offset=0`, предел `limit=100`.

| Метод и путь | Назначение |
| --- | --- |
| GET `/operators` | Типы, аргументы, результат и вес поддержанных операций |
| GET `/operators?include_extended=true` | Дополнительно formula и структурный aggregate-лист для нового клиента |
| GET `/sources/{source_id}/fields?q=&limit=&offset=` | Страничный ECS-каталог для собственного источника, включая причины несовместимости |
| GET `/sources/{source_id}/field-catalog?q=&limit=&offset=` | Полный ограниченный снимок полей конкретного источника с происхождением |
| POST `/validate` | Проверка структуры, типов, UTC-расписания и бюджета |
| POST `/preview` | Точный read-only снимок одного завершённого окна |
| POST корня | Создание после повторной серверной проверки и preview; обязателен `Idempotency-Key` |
| GET корня, GET `/{id}` | Список и карточка; удалённый агрегат остаётся доступен по UUID |
| GET `/{id}/points?limit=&offset=` | Сохранённые рабочие и исторические точки |
| GET `/{id}/copy` | Черновик, без создания второго агрегата |
| POST `/{id}/historical-points` | Чтение готовой canonical точки по границе без нового расчёта |
| POST `/{id}/archive`, POST `/{id}/resume` | Остановка и возобновление с явным пропущенным диапазоном |
| DELETE `/{id}` | Окончательная остановка новых расчётов с сохранением истории |

Основа запроса validate:

```json
{
  "source_id": "UUID собственного источника",
  "schedule": {
    "boundary": "2026-11-01T00:00:00+05:00",
    "timezone": "Asia/Yekaterinburg",
    "duration_seconds": 300
  },
  "aggregate_rule": {
    "where": {"op":"has_any","field":"event.category","value":["authentication"]},
    "features": [
      {"key":"events","name":"События","op":"count"},
      {"key":"failures","name":"Отказы","op":"count","where":{"op":"eq","field":"event.outcome","value":"failure"}},
      {"key":"ratio","name":"Доля отказов","op":"derive","expr":{"op":"divide","args":[{"ref":"failures"},{"ref":"events"}]}}
    ]
  }
}
```

Preview дополнительно принимает `window_start_utc` и явный `time_basis=event_time`.
Create также требует это основание. Старые формы принимаются транспортом
только для точного replay прежнего create; новый legacy запрос получает 422.
Create добавляет `name` и `rule_hash`, полученный при проверке. Один ключ с тем
же телом возвращает прежний UUID; другое тело с тем же ключом получает 409.
Сам хэш — SHA-256 канонического JSON с сохранением порядка признаков.

## Формулы над итогами окна

Сервер аддитивно поддерживает `op: "formula"` и необязательный корневой
`auxiliary`. Визуальный редактор и JSON поддерживают расширенный контракт;
старые сохранённые документы читаются без неявной миграции. Каталог `/operators` по умолчанию
сохраняет прежний ответ. Только явный `include_extended=true` добавляет formula
и описание aggregate-листа, список его базовых операций и допустимых параметров.

`features` — непустой упорядоченный выходной список. `auxiliary` отсутствует
либо является непустым списком определений того же вида; явные null и []
отвергаются. Ключи уникальны по обоим спискам. Вспомогательные признаки не
попадают в ValidationResult.feature_keys, PreviewResult.features, сохранённые
точки или вход модели. Card/copy сохраняют полное правило, точные литералы
и вспомогательные определения. Изменение сохранённого состава — новая копия
с новым UUID и отдельным детектором.

У formula обязательны key/name/op/expr; where допустим только при наличии
собственных агрегирующих листьев. Каждый узел expr имеет одну из форм:

```json
{"value": 100}
{"ref": "events"}
{"op": "divide", "args": [{"value": 100}, {"value": 2}]}
{"aggregate": {"op": "sum", "field": "network.bytes"}}
```

Числовые константы строгие, конечные; арифметические операции и арность те же,
что у derive. AggregateOperand содержит op, необязательный where и только
параметры выбранной базовой операции: field для всех, кроме count; percentile
только для percentile. Доступны все базовые статистики, счётчики и частоты.
Внутри aggregate запрещены derive/formula, refs, вложенная агрегация,
выражения над отдельными строками и произвольные поля. Смешанные ненулевые
формы узла отвергаются. Прежние nullable-поля сериализуются как раньше;
новое отсутствующее поле aggregate не добавляется как null.
Явный `aggregate:null` отвергается схемой Expression, включая вложенные узлы,
до сериализации и проверки прежней квитанции создания.

Первичный признак не имеет refs: например, одно отношение двух итогов окна:

```json
{
  "features": [{
    "key": "bytes_ratio", "name": "Отношение объёмов", "op": "formula",
    "expr": {"op": "ratio", "args": [
      {"aggregate": {"op": "sum", "field": "source.bytes"}},
      {"aggregate": {"op": "sum", "field": "destination.bytes"}}
    ]}
  }]
}
```

Производный признак имеет refs и может сочетать их с собственными итогами:

```json
{
  "auxiliary": [{"key": "events", "name": "Всего событий", "op": "count"}],
  "features": [{
    "key": "bytes_per_event", "name": "Байтов на событие", "op": "formula",
    "expr": {"op": "divide", "args": [
      {"aggregate": {"op": "sum", "field": "network.bytes"}},
      {"ref": "events"}
    ]}
  }]
}
```

В расширенном документе (formula или auxiliary) ссылки разрешаются по всему
объединённому набору определений; циклы, self-reference и неизвестные ключи
дают адресную ошибку. Детерминированный топологический порядок вычислений
не меняет порядок выхода features. Все определения проверяются, но runtime
рассчитывает только замыкание зависимостей выходов. Ошибка нужной зависимости
распространяется с причиной; неиспользуемый auxiliary не отравляет выход.
У прежнего документа derive по-прежнему ссылается только на предыдущие признаки.
Aggregate-лист запрещён внутри derive, даже в расширенном документе.

Для собственного листа применяется `rule.where AND feature.where AND
aggregate.where`. Ref получает уже рассчитанное значение зависимости с её
собственными условиями. Условие ссылающейся формулы не меняет зависимость.
Например, два count-листа могут отдельно отбирать event.action=logon и logoff,
а общий where ограничивать user.name=Andrew. Условие фильтрует события,
а не сравнивает готовый результат с порогом.

Все листья читаются в прежнем SQL-снимке с теми же границами и основанием
времени. Ошибки типов, пустые статистики, нулевой знаменатель и не конечные
результаты сохраняют null/reason; достоверность окна проверяется отдельно.
FeatureResult выходной формулы имеет valid_count=1 при успехе либо
invalid_count=1 при ошибке. Внутренние базовые статистики сохраняют собственные
счётчики входов. Значения и порядок одинаковы в preview, working points и
историческом расчёте прогрева; код детекторов получает прежний внешний контракт.

Канонический JSON/hash, request digest и replay старых квитанций не меняются.
Отсутствующие auxiliary/aggregate не появляются в старых ответах как null;
остальные прежние nullable-поля сохраняются. Действующие точки и checkpoints
не переписываются. Это проверяется golden-тестами относительно HEAD до расширения.

Бюджет включает все нужные внутренние статистики, условия и арифметику.
Одинаковые листья объединяются только при совпадении параметров и эффективных
условий. Distinct/квантили/частоты учитываются даже при единственном выходе.
Колонки SQL: `5 + 3 * число внутренних базовых статистик`, предел 1664.
Ширина ML-вектора равна только числу выходов; память дополнительно включает
1024 байта на каждый внутренний шаг. В расширенном документе число констант
выражений ограничено Limits.literals (256); прежние JSON/depth/списки условий,
time/memory/array limits не ослабляются. Сгенерированные внутренние имена и
AND-узлы не являются вторым пользовательским JSON-документом.

## Каталог полей источника

GET `/sources/{source_id}/field-catalog` требует только aggregates.read и
действующую сессию. Отдельные права на запись или чтение конфигурации
нормализатора не нужны. Гость получает 403; неизвестный источник — 404,
внешний — own_source_required (422). Значения событий, raw, константы,
регулярные выражения и конфигурация нормализатора в ответ не входят.

Один короткий read-only REPEATABLE READ читает источник, назначенный
нормализатор и все сохранённые нормализованные события source_id, без фильтра
по времени/availability и без выборки последних записей. Обход object-путей
выполняется в PostgreSQL; массив является значением поля, его индексы и
содержимое строк не превращаются в поля. Плоский ключ `"source.ip"` отличается
от вложенного source/ip. Null и пустой массив подтверждают присутствие ключа,
но не пригодность значения. В Python передаются пути, без ecs_data событий.

Предусмотренная часть включает map_ecs.target всех вариантов, в том числе
optional mappings, и системные @timestamp/ecs.version/event.original. Закрытая
schema/compiler проверяет rule без запуска нормализации. Повреждённая rule
даёт source_normalizer_invalid (422) без observed-only fallback и деталей rule.
Без событий доступны поля нормализатора; без нормализатора — наблюдавшиеся;
без обеих частей — пустой каталог. Смена назначения/версии и удаление последнего
события меняют соответствующую часть. Наличие поля не обещает значение в каждой
записи; исчезновение поля не отменяет нормативную проверку сохранённого правила.

Типы, описания, supported/reason и operators берутся из ECS 9.4.0. Неизвестные
JSON-ключи не предлагаются. Каталогизированный неподдержанный тип показывается
с причиной. Дополнительные поля каждого элемента:

```json
{"provenance": ["observed", "normalizer"], "normalizer_origin": ["mapping"]}
```

Provenance — непустое подмножество в указанном порядке; normalizer_origin —
отсортированное подмножество mapping/system, для observed-only пустое.
Ответ также содержит total/limit/offset, aware UTC snapshot_at, catalog_hash,
`observation: {"scope":"all_retained_events","complete":true,"rows":25}`
и `normalizer: {"id":"UUID","version":3}` либо null. complete относится
к полноте метаданных сохранённых событий, не к качеству агрегируемого окна.

q — буквальная регистронезависимая подстрока имени до 200 символов, без trim;
%, _, кавычки и обратная косая черта не являются шаблоном. limit=50 (1–100),
offset=0 (0–100000); сортировка стабильная по имени. Total и items используют
одинаковый фильтр после объединения. SHA-256 полного каталога включает ECS-версию
и identity/version нормализатора; не зависит от страницы, q, времени ответа
или числа событий с теми же полями. Транзакция между страницами не сохраняется.

Инъецируемый FieldCatalogLimits по умолчанию: deadline 10 с, 100000 событий,
64 MiB логического JSON, 2000000 посещённых узлов, глубина 16 сегментов,
8192 различных каталогизированных путей и work_mem 16 MiB. JSON-объём считается
через octet_length(ecs_data::text), включая хорошо сжимаемые строки; размер
rule нормализатора тоже входит в общий JSON-бюджет. Нормализаторная часть
проверяется по узлам/глубине/путям до выдачи ответа. Событийный обход считает
root, неизвестные пути и повторения до ECS-фильтра и DISTINCT; извлечение
останавливается на nodes+1. Preflight limit+1 нужен только для обнаружения
переполнения. Statement/lock timeout каждого чтения ограничены оставшимся
deadline. Превышение даёт field_catalog_budget_exceeded (422) с factor,
timeout — field_catalog_timeout (503). Нет partial/fallback/усечения даже
при q, limit=1 или offset за концом. Read-UoW всегда завершается; таблицы
инвентаря, cache и новый worker не создаются. Произвольный объём не обещается.

До чтения rule SQL-размер octet_length(rule::text) вместе с объёмом событий
проверяется по общему транспортному JSON-бюджету каталога. Превышение даёт
field_catalog_budget_exceeded/json_bytes без загрузки rule. Этот размер
не эквивалентен Python JSON-сериализации: PostgreSQL разворачивает малые float
в десятичную запись. Собственный прежний лимит нормализатора
(MAX_RULE_BYTES=65536) и грамматику проверяет его compiler после ограниченной
загрузки и обхода; недопустимое правило даёт source_normalizer_invalid (422).
Node-budget ограничивает обход уже декодированного JSON; первоначальная
десериализация ограничена транспортным byte-budget. После чтения rule deadline проверяется
безусловно до Python-обхода. Дети dict/list перечисляются лениво; стек хранит
только итераторы текущего пути, без предварительного раскрытия siblings.
До отказа допустимо прочитать лишь следующий узел обнаружения превышения;
периодические и финальная проверки общего deadline сохраняются.

## Каталог операций

`/operators` сохраняет прежние поля и публикует `compatible_fields` (точные
пары ECS-type/is_array), `arity`, обязательные `parameters`, их типы, nullable
и вес. `/sources/{id}/fields` дополнительно возвращает допустимые `operators`.
Неподдержанные поля и вложенные nested/flattened имеют явную причину.
Имена полей берутся только из поставляемого ECS 9.4.0. Поддержка операции над
типом массива не добавляет отсутствующее в каталоге поле этого типа.

Скалярные типы: keyword, constant_keyword, wildcard, text, match_only_text,
boolean, long/integer/short/byte, float/double/scaled_float, date, ip.
Числа конечны, целые проверяются по разрядности и JSON-форме (1.0 не long).
Даты — ISO `YYYY-MM-DDTHH:mm:ss[.ffffff]Z` или с явным
`±HH:mm[:ss[.ffffff]]`, включая однозначный выход действующего нормализатора
`1900-01-01T00:00:00+05:21:10`. Календарная дата и смещение проверяются;
сравнение и ключи частот определяются абсолютным UTC-моментом, включая DST-fold.
SQL явно трактует локальную часть как UTC и вычитает проверенный interval
смещения, поэтому секунды/микросекунды смещения не теряются и TimeZone сессии
не участвует в разборе. Все casts защищены CASE. IP — отдельный IPv4/IPv6
без маски и zone ID.

Технический диапазон date-операций — абсолютные моменты от
`0001-01-01T00:00:00Z` до `9999-12-31T23:59:59.999999Z` включительно.
Проверяется итог после вычитания смещения, а не год локальной записи.
Литералы за границами дают адресный `422 / invalid_literal_type` по пути
условия/значения; например, `0001-01-01T00:00:00+01:00` отклоняется до SQL.
Сохранённая дата вне диапазона даёт `invalid_input_type`, null и invalid_count
у затронутого признака по прежней политике качества. Рабочая точка с причиной
сохраняется вместе с курсором, само значение не вызывает транспортный retry.
Это распространяется и на элементы date-массивов.

Внутри SQL date-значения передаются как `timestamp without time zone` с
техническим смыслом UTC; адаптер явно добавляет метку UTC после чтения.
Так край диапазона не превращается в BC/год 10000 из-за TimeZone драйвера.
Это не настройка TimeZone сессии и не подмена значения: сравнения, частоты
и границы ECS `@timestamp` используют те же абсолютные моменты. Ключи категорий
остаются в чистой логике `aggregation/`. Нормализатор, события и сохранённые
точки не переписываются.

| Условие | Аргументы и смысл | Вес |
| --- | --- | --- |
| `all`, `any` | args из одного или более условий | 1 |
| `not` | ровно одно условие в args | 1 |
| `eq`, `neq` | scalar field, строго типизированный value | 1 |
| `in`, `not_in` | scalar field, непустой однородный список value | 1 |
| `exists`, `not_exists` | scalar/typed-array field, без value | 1 |
| `gt`, `gte`, `lt`, `lte` | число или date, один value | 1 |
| `between` | число или date, два упорядоченных value, обе границы включены | 1 |
| `contains`, `starts_with` | строка, непустой буквальный value с учётом регистра | 2 |
| `in_cidr` | scalar ip, IPv4/IPv6 CIDR value; другая семья не совпадает | 2 |
| `has_any` | typed-array, непустой однородный список value; хотя бы один элемент | 1 |
| `has_all`, `has_none` | typed-array, все / ни одного элемента из value | 2 |

`neq`/`not_in` требуют присутствующего ненулевого значения. `not` может
совпасть с отсутствием/null, но никогда с ошибкой типа дочернего условия.
Ошибки всех дочерних условий сохраняются независимо от короткого замыкания.
Пустая строка и пустой массив присутствуют. Пустой массив даёт false для
has_any/has_all и true для has_none; отсутствующий/null не совпадает ни с одним
has-условием. Неоднородный массив, null/объект/массив внутри него — неверный тип.
Массивы допускают те же скалярные типы элементов; скалярные операции массив
не принимают. Строки `%`, `_`, кавычки, обратный слеш и Unicode буквальны.

| Базовый признак | Поле / результат | Вес |
| --- | --- | --- |
| `count` | без поля, число выбранных записей | 1 |
| `distinct_count` | scalar, точное число уникальных присутствующих значений | 8 |
| `sum`, `avg`, `min`, `max` | число, сумма/среднее/минимум/максимум | 2 |
| `present_count`, `missing_count` | scalar/typed-array, наличие правильного типа / отсутствие или null | 1 |
| `true_count`, `false_count` | scalar boolean, число true / false | 1 |
| `range` | число, max − min | 4 |
| `variance`, `stddev` | число, генеральная дисперсия (делитель N) / её корень | 4 |
| `median`, `percentile` | число, непрерывный квантиль полного набора | 12 |
| `mode_count`, `mode_share` | scalar, частота моды / её доля среди присутствующих значений | 12 |
| `derive` | выражение expr | 0 |

Только percentile требует дополнительный параметр `percentile` от 0 до 1;
median равна percentile 0.5. Для отсортированного набора размера N позиция
`p*(N-1)`, между соседними значениями — линейная интерполяция. Входные long
не преобразуются в binary64: SQL сохраняет numeric, интерполяция — Decimal
с точностью 100 десятичных цифр. Целый результат возвращается JSON integer
без потери int64; дробный результат API округляется до ближайшего binary64
при преобразовании Decimal в float (включая дроби рядом с границей int64).
Это округление представления, а не выборочное приближение квантиля.
variance/stddev используют PostgreSQL numeric population statistics; возможна
разница последнего разряда с вычислением binary64.

На пустом наборе count/distinct/present/missing/true/false равны 0;
остальные статистики, включая частоту и долю моды, дают null/no_values.
При одном числе range/variance/stddev равны 0. Категория моды не сохраняется;
ничья частот не меняет числовой результат. valid_count у четырёх новых
счётчиков — число записей соответствующего подсчёта, у моды — знаменатель.

В документе без formula/auxiliary прежние derive-выражения используют ссылки на ранее объявленные признаки
`{"ref":"key"}` и числовые константы `{"value":2}`. Вес каждого узла — 1.
Бинарные add/subtract/multiply/divide и ratio (синоним divide) имеют два args;
percent, per_second, abs — один; clamp — три (значение, нижняя и верхняя
границы); min_of/max_of — два или более. percent умножает долю на 100,
per_second делит на сохранённую длительность окна, abs берёт модуль,
clamp ограничивает замкнутым диапазоном, min_of/max_of выбирают экстремум.
Обратные границы clamp дают `invalid_clamp_bounds`. Прежние коды причин
сохранены; нулевой ratio имеет `division_by_zero`.

Пример дополнительных признаков:

```json
{
  "where": {"op":"in_cidr","field":"source.ip","value":"192.0.2.0/24"},
  "features": [
    {"key":"p95","name":"95-й перцентиль байтов","op":"percentile","field":"network.bytes","percentile":0.95},
    {"key":"share","name":"Доля частого метода","op":"mode_share","field":"http.request.method"},
    {"key":"percent","name":"Процент","op":"derive","expr":{"op":"percent","args":[{"ref":"share"}]}}
  ]
}
```

Каждый результат содержит `value`, `reason`, `valid_count`, `invalid_count`.
Для базовых признаков счётчики относятся к участвующим записям; для производных
`valid_count=1` при успешном вычислении, иначе `invalid_count=1`.
Отсутствие поля и JSON null не заменяются нулём. Неверный тип, включая
неоднородный массив в условии, отравляет затронутый признак с
`invalid_input_type`. Пустые числовые статистики имеют `no_values`, деление
на ноль — `division_by_zero`, отсутствующий операнд — `missing_operand`,
переполнение — `non_finite_result`. Ноль count/distinct сам по себе не
доказывает полноту покрытия.
Защитная проверка нечислового/не конечного операнда использует отдельные
`non_numeric_operand`/`non_finite_operand`; преобразование строки в число не выполняется.

## Прежние снимки availability: историческое основание

После 0021 эти агрегаты сохраняются как availability_v1/retired. Их прежние
working/historical payload, основания времени, квитанции и модели доступны
для чтения и явной очистки; новые расчёты не выполняются. Копия создаёт черновик
нового event_time агрегата и требует новых validate/preview/create.

Общие атомарные event/processed-record/marker, pgoutput, capture progress,
подписанные input attestations и Kafka diagnostics продолжают работать для
приёма и диагностики. Их технические времена не задают принадлежность событийному
окну. Старые команды пересчёта через availability/barrier удалены.

## Событийный серверный процесс

Новые агрегаты имеют `semantic_basis=event_time`, `execution_mode=current`.
Прежние объекты атомарно переведены в `availability_v1`/`retired` с причиной
`aggregate_time_semantics_retired`; их состояния lifecycle и основания времени
отдельных точек сохранены. Все прежние детекторы fenced и необратимо terminated,
checkpoint/inputs/findings не сбрасываются. DB guards запрещают старому writer
новую точку, авторизацию модели и продвижение её результатов после retirement.
Создание новых объектов не имеет молчаливого server default временной семантики.

List/card/points/copy и ручная очистка retired истории доступны. Новый расчёт,
start/resume/unarchive запрещены с 409; новая копия требует validate/preview,
нового UUID и отдельного детектора. Exact create replay проверяет прежний
actor:key/digest, включая omitted time_basis/default serialization, и возвращает
прежнюю retired карточку. Другой body с тем же key — idempotency_conflict,
новый legacy body/key — legacy_calculation_removed. AST проверяется до replay.
Downgrade непустой подсистемы явно отказывает (пустая допускает возврат схемы): автоматического переименования семантики или удаления
сохранённых данных ради обратного перехода нет.

Сетка `[anchor+n*D,anchor+(n+1)*D)`, canonical n>=0, D=1..604800 целых секунд.
Пояс ввода однократно задаёт UTC-якорь. Preview может проверить завершённое
окно до anchor с `in_process=false`; оно не входит в историю или прогрев.
При create часы БД фиксируют bootstrap_at и online_start_index содержащего
его окна (при будущем anchor — 0). Более ранние окна — initial_history,
остальные — online; пауза, старение и restart эту границу не меняют.

Discovery и online имеют отдельные сохраняемые позиции. Старая история
рассчитывается порциями, включая последнее завершённое окно архива, без EOF,
следующего события и таймера от обнаружения. До известной истории и от конца
старого архива до online-границы нормальная пустота не достраивается.
Online close_not_before_at=end+min(D,300 секунд); нового события ждать не нужно.
Истечение срока само по себе не закрывает окно: используются записи фактически
зафиксированного снимка. Restart/unpause сохраняют прежние сроки и позицию.

Короткий schedule-lock назначает window/origin/generation. Отдельный read-only
RR вне lifecycle-lock читает candidate: пригодные события ДО where, features,
cohort/evidence и исключения. Финальный write UoW под тем же mutex перепроверяет
состояние/generation/назначение/deadline и атомарно сохраняет payload, closure,
membership и cursor. Уникальная schedule/index и стабильный UUID сохраняются
после очистки; неизвестный commit не разрешает пересчитать закрытое окно другим
снимком. В read-only RR запись не выполняется.

Пригодность времени требует durable processing provenance. Missing, invalid,
fallback и unknown provenance различимы; default diagnostics=[] её не доказывает.
`@timestamp` позже единого snapshot_reference_at получает event_time_future и
не продвигает ряд. До закрытия следующий проход может признать дату наступившей;
сохранённый результат при этом не улучшается. Collected_at и текущий normalizer
не восстанавливают отсутствующее исходное время.

Качество received_event_snapshot отделено от delivery_coverage=not_attested.
Отсутствие необязательного probe само по себе не запрещает архивный прогрев.
Известная остановка даёт interrupted; потери, processing failures, backlog и
неразрешённые временные исключения — unknown. Cohort относится к технической
загрузке, а не подменяется датой старого архива. Unknown/interrupted и null
координаты не обучают RCF как нормальный ноль.

Closure хранит stable origin_point_id, source/window/basis/origin, моменты
снимка/закрытия и present/cleared. Точное membership event_id сохраняется после
удаления payload/raw: это свидетельство участия, а не копия исходных журналов
или полного числового ряда. Отпечаток — SHA-256 точного JSONB-массива
[ecs_data,normalization_diagnostics], без float преобразования исходных чисел.
Overlap-прогрев проверяет эти fingerprints и не добавляет свежие late.

Циклическое обследование сохраняет late по UNIQUE(closure,event_id), с периодом,
причиной и обнаружением. UUID задаёт порядок страницы, а не commit watermark:
после конца обход начинается заново. Late не переносится в период загрузки,
не меняет features/quality/model/finding. Очистка/raw deletion не превращают
прежних участников в late. Для retired истории membership не реконструируется
и новый late scan не выполняется.

## Пауза и ручная очистка

POST `/{id}/pause` и `/unpause` — отдельные commands с Idempotency-Key,
aggregates.write и CSRF; `/resume` остаётся unarchive. Mutation и immutable
receipt сохраняются одним UoW. Replay прежней pause после unpause возвращает
квитанцию без повторного действия; актуальное состояние читается карточкой.
После подтверждения паузы stale candidate не фиксирует точку/курсор.
Разрешённые модели ждут; stopped детектор автоматически не запускается.
Ingest и другие агрегаты продолжают работу.

| Метод и путь | Результат |
| --- | --- |
| GET `/{id}/points/cleanup-preview?keep_last=N` | Read-only protection plan |
| POST `/{id}/points/cleanup`, body `{keep_last:N}` | 202 immutable accepted receipt |
| GET `/{id}/cleanup-operations/{operation_id}` | pending/running/succeeded/failed и progress |
| POST `/{id}/cleanup-operations/{operation_id}/retry` | Явное продолжение failed с тем же cutoff |
| GET `/{id}/points/by-index/{index}` | Сохранённая canonical точка, 410 cleared либо 409 not-ready |

N — количество последних payload по порядку окон, не offset. JSON требует
StrictInt 0..int64max; query — десятичную строку без знака/дроби/экспоненты.
N>=K — корректный no-op; N=0 разрешён при отсутствии зависимостей.
Автоматическая retention-политика не вводится.

Все исполняемые связанные детекторы должны быть подтверждённо stopped.
Retired terminal модели необратимо остановлены и имеют M_i=0. При валидном
checkpoint защищается хвост после consumed_index: skipped тоже потреблены,
история модели уже в checkpoint. Без checkpoint используется тот же ограниченный
ordinary/accelerated planner, что при start. Самодостаточные prepared inputs
сохраняются для повторного запуска. M=max(M_i), максимум удаления K-M;
N<M отклоняется целиком с UUID/именами/защищёнными границами. Непроверяемая
защита даёт cleanup_protection_unavailable, а не частичный M.

Порядок locks — key → schedule → detectors по UUID. Сервер перепроверяет plan
и фиксирует operation/cutoff/receipt/fence атомарно. Пока active_cleanup задан,
новые close/start/create и конфликтующий lifecycle получают cleanup_in_progress.
Существующий worker освобождает payload/тяжёлые fingerprint-данные порциями;
прогресс каждой порции атомарен. Failed сохраняет fence/progress; новый command
key явно возобновляет ту же операцию. 202 не означает succeeded.

Очистка не сбрасывает cursor и не воссоздаёт закрытые окна. Исходные ECS,
checkpoint и Finding snapshots сохраняются. Находка не удерживает point payload;
Outcome после очистки становится тонким, у детектора остаётся не более двух
полных проекций last_consumed/last_evaluated. Points list считает только present.
Lookup очищенного окна даёт 410 aggregate_point_cleared, незакрытого —
409 canonical_point_not_ready; historical API читает canonical результат.
GET /{id}/points/{point_id} читает сохранённую identity и также возвращает
410 после очистки; неизвестная или чужая identity даёт 404.

## Ресурсные границы

Стартовые значения задаёт `Limits`; каждое можно конфигурировать переменной
`AGGREGATE_<ИМЯ_ПОЛЯ_В_ВЕРХНЕМ_РЕГИСТРЕ>` в окружении API и worker одинаково.
`work_mem_mb` не может превышать 32. Порог в пять признаков отсутствует.

| Поле | Значение |
| --- | --- |
| `json_bytes` | 65536 |
| `depth` | 8 |
| `literals` | 256 |
| `preview_rows` | 100000, без усечения |
| `cost` | 50000000 |
| `preview_timeout_ms` | 10000 на весь preview |
| `working_timeout_ms` | 30000 на весь close, включая запись |
| `work_mem_mb` | 32 на операцию плана |
| `total_memory_mb` | 256, отдельная оценка совокупной памяти |
| `array_elements` | 4096 элементов одного сохранённого массива, без усечения |

Стоимость — `estimated_rows * sum(operator_weight)`: count и узел условия = 1,
числовая статистика = 2, exact distinct = 8, узел арифметического выражения = 1.
Веса расширенных операций приведены в каталоге выше; прежние веса сохранены.
Для `has_all` и `has_none` эффективный вес одного условия — `2 * len(value)`:
компилятор выполняет отдельное типизированное EXISTS-сканирование для каждого
литерала. Для `has_any` над новыми типами элементов вес — `len(value)`.
Для прежних keyword/constant_keyword-массивов `has_any` сохраняет принятый вес 1.
Размер списка считается до какой-либо дедупликации; лимит 256 и отсутствие
усечения сохраняются. Формула опубликована в `weight_formula` каталога.
Например, count + has_none при 1 строке шириной 22000 байт дают стоимость
`(1 + 2*L) * ceil(22000/256)`: 258 при L=1 и 44118 при L=256.
Превышение лимита даёт `resource_budget_exceeded`, фактор `operator_cost`;
следует сократить список, окно или сложность правила. Частичная точка и
продвижение курсора при таком отказе не сохраняются.
Для правил с новыми операциями или новыми поддержанными типами стоимость
дополнительно умножается на `ceil(row_width/256)`: длинные строки и массивы
не оцениваются как короткий скаляр. Для них же резервируются `4*row_width`
байт временной памяти при непустом входе. Прежние оценки старых правил сохранены.
Общее where расширенного правила материализуется один раз в том же SQL-снимке;
его буфер дополнительно учитывается как `min(rows*(row_width+16), work_mem_bytes)`.
Это исключает повторение сложного предиката в каждой колонке статистики;
избыток tuplestore PostgreSQL может вынести на диск в рамках timeout.
Оценка совокупной памяти — `(distinct_features + 4 * materialized_features) * rows * row_width + vector_width * 1024`
байт; `row_width=max(256, max(octet_length(ecs_data::text))+64)` по выбранному окну.
materialized_features — число median/percentile/mode_count/mode_share: учитываются
полные массивы SQL, значения драйвера и Python sort/Counter, а не только work_mem.
Большие строки и массивы входят в row_width; память частот оценивается по
верхней границе кардинальности rows. Превышение array_elements возвращает
resource_budget_exceeded с фактором array_elements и именем переменной
AGGREGATE_ARRAY_ELEMENTS. Ни точка, ни частичный ответ не сохраняются.
Это консервативная стартовая оценка несжатого состояния, а не гарантия
пикового потребления PostgreSQL. Кардинальность оценивается верхней границей по
числу строк. API также показывает общий объём источника и предварительную
оценку RCF `vector_width * 100 * 256 * 8` байт; конкретные параметры детектора
будут проверяться при его создании. Runtime-ошибки и отставание остаются видимы.
Timeout в 30 секунд не обещает своевременность секундного окна при любом потоке.
Сервис устанавливает `SET LOCAL jit=off` вместе с timeout/work_mem только в
транзакции расчёта: сложные защищённые JSON-выражения не должны тратить время
секундного окна на компиляцию сотен LLVM-функций. Настройка всей БД не меняется.
SQL-план отдельно проверяется на предел PostgreSQL в 1664 выходные колонки:
текущая компиляция использует `5 + 3 * число_нужных_базовых_статистик`. Размер массива
и ширина строки передаются одной внутренней колонкой, чтобы сохранить прежнюю
допустимую ширину SQL-плана. Ошибка
`statement_width` предлагает разделить базовые признаки между агрегатами.
Это ограничение конкретного SQL-плана; производные признаки не добавляют ему
колонок, и самостоятельного фиксированного лимита ширины вектора нет.

## Повторяемая проверка

Новый серверный путь проверяется адресно:

```powershell
python -B scripts/agent_test_profiles.py backend-db --pytest tests/test_event_time_contracts.py tests/test_event_time_pipeline.py
python -B scripts/agent_test_profiles.py backend-db --rcf --pytest tests/ml/event_time.py
python -B scripts/agent_test_profiles.py smoke-development --aggregate-only
python -B scripts/agent_test_profiles.py smoke-production --aggregate-only
```

Event-time candidate ограничен 100000 пригодных событий и 64 MiB снимка,
общая расчётная память с manifest — 256 MiB. Каждый SQL получает остаток общего
deadline, work_mem<=32 MiB. Discovery/late: страница<=500 и turn<=1 с, с новым
циклом от начала; один turn закрывает максимум одно окно, pool<=4. Cleanup:
<=256 payload за turn<=5 с, <=5000 зависимых строк за SQL-порцию, lock timeout
1 с. Постоянные closure/membership/late и самостоятельные результаты моделей
не входят в освобождаемые payload; произвольный объём не обещается.

Адресные регрессии формул/каталога и интеграция окончательного вектора с
неизменённым детектором входят в существующие профили:

```powershell
python -B scripts/agent_test_profiles.py backend-db --pytest tests/test_aggregate_formulas.py tests/test_aggregate_field_catalog.py
python -B scripts/agent_test_profiles.py backend-db --rcf --pytest tests/ml/rcf_service.py
```

Новый ML-сценарий использует атомарный writer, настоящий pgoutput, подписанные
аттестации и независимо публикуемые checkpoints внутри одноразовой PostgreSQL.
Время availability и complete не назначаются вручную. Проверяются оба прогрева,
один окончательный выход при нескольких внутренних шагах, одинаковые значения
preview/working/history, восстановление checkpoint и пропуск unknown/interrupted.
Для него используются принятые live-параметры trees=20/sample=8/outputAfter=8;
defaults продукта и ресурсные пределы остаются прежними.

Общие команды полной приёмки выбираются по политике затронутых компонентов:

```powershell
python -B scripts/agent_test_profiles.py backend-db
python -B scripts/check_pgoutput_gate.py
python -B scripts/agent_test_profiles.py kafka-integration --pytest tests/test_window_kafka_evidence.py
python -B scripts/agent_test_profiles.py end-to-end --aggregate-only
```

Последняя команда использует обычный development-контур и проверяет proxy/API,
настоящие decoder/worker, D=5, старый архив, late, паузу и восполнение после
простоя, оба RCF-прогрева и защиту очистки несколькими моделями. Оба smoke также
используют этот серверный сценарий. Все стенды и секреты временные; очистка и
сравнение Docker-инвентаря выполняются общим runner.
