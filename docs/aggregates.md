# Серверные агрегаты

Агрегаты работают только с собственными ECS-источниками PostgreSQL. Сохранённые
правило, порядок признаков, источник и расписание неизменяемы. Копия возвращает
черновик для создания нового UUID. RCF и пользовательский интерфейс агрегатов
вводятся отдельными задачами.

## API

Все маршруты находятся под `/api/v1/aggregates`. Администратору доступны
`aggregates.read` и `aggregates.write`; Guest эти права не получает.
POST и DELETE требуют действующей сессии и `X-CSRF-Token`.
Точные типы запросов и ответов публикуются OpenAPI в development.

| Метод и путь | Назначение |
| --- | --- |
| GET `/operators` | Типы, аргументы, результат и вес поддержанных операций |
| GET `/sources/{source_id}/fields?q=&limit=&offset=` | Страничный ECS-каталог для собственного источника, включая причины несовместимости |
| POST `/validate` | Проверка структуры, типов, UTC-расписания и бюджета |
| POST `/preview` | Точный read-only снимок одного завершённого окна |
| POST корня | Создание после повторной серверной проверки и preview; обязателен `Idempotency-Key` |
| GET корня, GET `/{id}` | Список и карточка; удалённый агрегат остаётся доступен по UUID |
| GET `/{id}/points?limit=&offset=` | Сохранённые рабочие и исторические точки |
| GET `/{id}/copy` | Черновик, без создания второго агрегата |
| POST `/{id}/historical-points` | Сохранение одного исторического окна, тело `{"window_start_utc":"…"}` |
| POST `/{id}/archive`, POST `/{id}/resume` | Остановка и возобновление с явным пропущенным диапазоном |
| DELETE `/{id}` | Окончательная остановка новых расчётов с сохранением истории |

Основа запроса validate:

```json
{
  "source_id": "UUID собственного источника",
  "schedule": {
    "boundary": "2026-11-01T00:00:00+05:00",
    "timezone": "Asia/Yekaterinburg",
    "duration_seconds": 300
  },
  "aggregate_rule": {
    "where": {"op":"has_any","field":"event.category","value":["authentication"]},
    "features": [
      {"key":"events","name":"События","op":"count"},
      {"key":"failures","name":"Отказы","op":"count","where":{"op":"eq","field":"event.outcome","value":"failure"}},
      {"key":"ratio","name":"Доля отказов","op":"derive","expr":{"op":"divide","args":[{"ref":"failures"},{"ref":"events"}]}}
    ]
  }
}
```

Preview дополнительно принимает `window_start_utc` и `time_basis`:
`availability_at` либо явно выбранный `backend_processed_at_historical`.
Create добавляет `name` и `rule_hash`, полученный при проверке. Один ключ с тем
же телом возвращает прежний UUID; другое тело с тем же ключом получает 409.
Сам хэш — SHA-256 канонического JSON с сохранением порядка признаков.

Условия ядра: `all`/`any`, `eq`/`in`/`exists`/`not_exists` по скалярным ECS
keyword, boolean и числам; `has_any` по типизированным keyword-массивам.
Признаки: `count`, точный `distinct_count`, `sum`/`avg`/`min`/`max`, `derive` с
`add`/`subtract`/`multiply`/`divide`. Константа выражения — `{"value":2}`,
ссылка — `{"ref":"ранее_названный_key"}`. Другие операции отвергаются.

Каждый результат содержит `value`, `reason`, `valid_count`, `invalid_count`.
Для базовых признаков счётчики относятся к участвующим записям; для производных
`valid_count=1` при успешном вычислении, иначе `invalid_count=1`.
Отсутствие поля и JSON null не заменяются нулём. Неверный тип, включая
неоднородный массив в условии, отравляет затронутый признак с
`invalid_input_type`. Пустые числовые статистики имеют `no_values`, деление
на ноль — `division_by_zero`, отсутствующий операнд — `missing_operand`,
переполнение — `non_finite_result`. Ноль count/distinct сам по себе не
доказывает полноту покрытия.
Защитная проверка нечислового/не конечного операнда использует отдельные
`non_numeric_operand`/`non_finite_operand`; преобразование строки в число не выполняется.

## Время и атомарность

Рабочее окно определяется сохранённым UTC-якорем и длительностью 1…604800
секунд. `scheduled_at=end_utc`; часовой пояс используется для ввода и
представления. Первый рабочий start не раньше времени создания.
Постоянный `aggregate-worker` в обоих Compose-режимах ждёт миграций и здорового
WAL-декодера. Окно закрывается только после материализации барьера TASK-30;
вход выбирается по полуоткрытому интервалу `availability_at`.

Для отдельного перезапуска используйте `restart --no-deps aggregate-worker`
с теми же Compose-файлами и окружением. После `stop` существующий контейнер
запускается через `up -d --no-deps --no-build aggregate-worker`.

Признаки, число событий и границы ECS `@timestamp` читаются одним SQL statement.
Полная точка и следующий индекс сохраняются одной транзакцией под блокировкой
расписания. Ошибка/timeout откатывает обе записи; worker сохраняет безопасную
диагностику и повторяет расчёт с ограниченным backoff. Остальные агрегаты
продолжают обрабатываться. После простоя активные окна восполняются по порядку.
Один worker выполняет не более четырёх независимых расчётов одновременно;
бюджет плана не является глобальным ограничителем памяти всех worker и БД.
Архивирование, возобновление, исторический расчёт и удаление берут ту же
блокировку расписания; барьер не разрешает запись после удаления.

Исторический запрос не двигает рабочий курсор. Окно должно быть выровнено и
закончиться не позже создания агрегата. Повтор возвращает неизменяемую точку.
Для availability-истории используется отдельный долговечно материализованный
барьер. Preview не создаёт барьер. Без уже сохранённых барьера и доказательств
покрытия он помечается `unverified`: сам снимок не доказывает полного покрытия.

## Обновление capture

Перед первым bootstrap и перед обновлением существующей установки остановите
все старые API/consumer/writer-процессы, worker агрегатов и WAL-декодер. Затем выполните миграции, bootstrap,
дождитесь готовности декодера и запускайте обновлённые API/worker. Не запускайте
две версии writer одновременно.
Bootstrap отказывает при обнаружении активной записи/блокировки writer на
источниках или событиях. После bootstrap отложенный constraint trigger проверяет
наличие маркера у каждой новой записи в момент commit и отклоняет старый writer
без маркера. Это дополнительная защита к обязательной остановке старых процессов.

Первая инициализация без прежнего прогресса/маркеров сохраняет одним действием
`legacy_cutover_at` и `availability_verified_from_at` по времени БД. Повторный
bootstrap их не сдвигает. Для прежней установки первая граница остаётся NULL;
новый upgrade-барьер даёт только будущую консервативную границу после
материализации. Даты не восстанавливаются из heartbeat, LSN или ручного ввода.

Сохраняемая старая история разрешена только до известного `legacy_cutover_at`
и только по записям без маркера. Availability-история разрешена только начиная с
`availability_verified_from_at`; markerless-запись в таком окне вызывает отказ.
Пересечение границ или неизвестная область дают `historical_time_basis_unknown`.
Явный ретроспективный preview по времени обработки остаётся read-only и
`unverified`, в том числе для старой установки с неизвестной первой границей.

## Ресурсные границы

Стартовые значения задаёт `Limits`; каждое можно конфигурировать переменной
`AGGREGATE_<ИМЯ_ПОЛЯ_В_ВЕРХНЕМ_РЕГИСТРЕ>` в окружении API и worker одинаково.
`work_mem_mb` не может превышать 32. Порог в пять признаков отсутствует.

| Поле | Значение |
| --- | --- |
| `json_bytes` | 65536 |
| `depth` | 8 |
| `literals` | 256 |
| `preview_rows` | 100000, без усечения |
| `cost` | 50000000 |
| `preview_timeout_ms` | 10000 на SQL statement |
| `working_timeout_ms` | 30000 на SQL statement |
| `work_mem_mb` | 32 на операцию плана |
| `total_memory_mb` | 256, отдельная оценка совокупной памяти |

Стоимость — `estimated_rows * sum(operator_weight)`: count и узел условия = 1,
числовая статистика = 2, exact distinct = 8, узел арифметического выражения = 1.
Оценка совокупной памяти — `distinct_features * rows * row_width + vector_width * 1024`
байт; `row_width=max(256, max(octet_length(ecs_data::text))+64)` по выбранному окну.
Это консервативная стартовая оценка несжатого состояния, а не гарантия
пикового потребления PostgreSQL. Кардинальность оценивается верхней границей по
числу строк. API также показывает общий объём источника и предварительную
оценку RCF `vector_width * 100 * 256 * 8` байт; конкретные параметры детектора
будут проверяться при его создании. Runtime-ошибки и отставание остаются видимы.
Timeout в 30 секунд не обещает своевременность секундного окна при любом потоке.
SQL-план отдельно проверяется на предел PostgreSQL в 1664 выходные колонки:
текущая компиляция использует `5 + 3 * число_базовых_признаков`. Ошибка
`statement_width` предлагает разделить базовые признаки между агрегатами.
Это ограничение конкретного SQL-плана; производные признаки не добавляют ему
колонок, и самостоятельного фиксированного лимита ширины вектора нет.

## Повторяемая проверка

```powershell
python -B scripts/agent_test_profiles.py backend-db
python -B scripts/check_pgoutput_gate.py
python -B scripts/agent_test_profiles.py kafka-integration --pytest tests/test_window_kafka_evidence.py
python -B scripts/agent_test_profiles.py end-to-end --aggregate-only
```

Последняя команда использует обычный development-контур и проверяет proxy/API,
настоящие decoder/worker, секундные окна, отдельный исторический барьер,
восполнение после простоя, два worker, архивирование и удаление. Оба штатных
smoke-профиля также выполняют этот сценарий. Все стенды и их секреты временные;
очистка и сравнение Docker-инвентаря выполняются общим runner.
