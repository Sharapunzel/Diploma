# Серверные агрегаты

Агрегаты работают только с собственными ECS-источниками PostgreSQL. Сохранённые
правило, порядок признаков, источник и расписание неизменяемы. Копия возвращает
черновик для создания нового UUID. Серверное ядро RCF и его ограниченная
административная CLI описаны в [контракте детекторов](detectors.md).

## Интерфейс

Раздел «Аномалии → Агрегаты» доступен с `aggregates.read`; создание и действия
требуют `aggregates.write`. Маршруты: `/aggregates`, `/aggregates/new`,
`/aggregates/{id}`. JSON-режим редактирует только `aggregate_rule`; визуальный
режим использует тот же документ и полный серверный каталог операций.
Числовые литералы и ответы проходят изолированный `lossless-json` 4.3.3:
большие целые и различие `1`/`1.0` сохраняются. Нераспознанный JSON остаётся
доступен для исправления и не заменяется старым правилом.

Укажите собственный источник, исходную ISO-границу с явным смещением,
согласованный IANA-пояс, длительность 1–604800 секунд и начало завершённого
выровненного preview-окна. Выполните «Проверить правило», «Предварительный
расчёт», затем «Создать агрегат». Изменение контекста отменяет прежнюю проверку.
После неизвестного результата создания явный повтор неизменённого тела
использует тот же Idempotency-Key. Автоматического повтора изменений нет.

Карточка показывает неизменяемые параметры, расписание, диагностику и точки.
Архивирование и удаление требуют подтверждения. Запрос одного исторического
окна явный и не двигает рабочий курсор; недоказанное основание истории
не подтверждается вручную. График относится только к загруженной странице
(50 точек), с отдельными видами рабочей/исторической точки и разрывами на
пропусках, null и неподтверждённой полноте. Координаты приближённые; таблица
сохраняет точные значения, причины и количество корректных/некорректных входов.
Пояс отображения меняет подписи, сохраняя UTC-расписание и исходные ISO-строки.

«Промпт для ИИ» загружает полный каталог полей выбранного источника по страницам,
показывает инструкцию до копирования и не вызывает внешнюю модель. Каталог
не подтверждает присутствие полей в данных. При отказе clipboard доступно
ручное копирование.

Frontend-проверки запускаются `python -B scripts/agent_test_profiles.py frontend`.
Команда `python -B scripts/agent_test_profiles.py end-to-end --aggregate-only`
также запускает `aggregates.live.spec.ts` и `aggregates.ui.spec.ts`: реальные
создание/preview/worker/история на двух источниках и моделируемые отказы,
права гостя, подтверждения, clipboard и адаптив. Синтетические пользователь,
источники и время передаются браузеру до очистки серверного сценария через
`AGGREGATE_BROWSER_CONFIG`; самостоятельно запускать live-spec против рабочей
БД не следует. Контейнеры, тома, сеть, builder/cache, временные секреты и
браузерные артефакты принадлежат единому runner и удаляются в его `finally`.

## API

Все маршруты находятся под `/api/v1/aggregates`. Администратору доступны
`aggregates.read` и `aggregates.write`; Guest эти права не получает.
POST и DELETE требуют действующей сессии и `X-CSRF-Token`.
Точные типы запросов и ответов публикуются OpenAPI в development.

GET списка принимает необязательные `q` (до 200 символов, пробелы по краям
удаляются) и `state=active|archived`. Поиск — регистронезависимая буквальная
подстрока имени по всему каталогу; `%`, `_`, обратная косая черта и кавычки
не становятся шаблоном или SQL. Удалённые записи исключаются. `total` и `items`
учитывают одинаковые фильтры, порядок — `created_at DESC, id DESC`.
Без фильтров поведение сохраняется: `limit=50`, `offset=0`, предел `limit=100`.

| Метод и путь | Назначение |
| --- | --- |
| GET `/operators` | Типы, аргументы, результат и вес поддержанных операций |
| GET `/sources/{source_id}/fields?q=&limit=&offset=` | Страничный ECS-каталог для собственного источника, включая причины несовместимости |
| POST `/validate` | Проверка структуры, типов, UTC-расписания и бюджета |
| POST `/preview` | Точный read-only снимок одного завершённого окна |
| POST корня | Создание после повторной серверной проверки и preview; обязателен `Idempotency-Key` |
| GET корня, GET `/{id}` | Список и карточка; удалённый агрегат остаётся доступен по UUID |
| GET `/{id}/points?limit=&offset=` | Сохранённые рабочие и исторические точки |
| GET `/{id}/copy` | Черновик, без создания второго агрегата |
| POST `/{id}/historical-points` | Сохранение одного исторического окна, тело `{"window_start_utc":"…"}` |
| POST `/{id}/archive`, POST `/{id}/resume` | Остановка и возобновление с явным пропущенным диапазоном |
| DELETE `/{id}` | Окончательная остановка новых расчётов с сохранением истории |

Основа запроса validate:

```json
{
  "source_id": "UUID собственного источника",
  "schedule": {
    "boundary": "2026-11-01T00:00:00+05:00",
    "timezone": "Asia/Yekaterinburg",
    "duration_seconds": 300
  },
  "aggregate_rule": {
    "where": {"op":"has_any","field":"event.category","value":["authentication"]},
    "features": [
      {"key":"events","name":"События","op":"count"},
      {"key":"failures","name":"Отказы","op":"count","where":{"op":"eq","field":"event.outcome","value":"failure"}},
      {"key":"ratio","name":"Доля отказов","op":"derive","expr":{"op":"divide","args":[{"ref":"failures"},{"ref":"events"}]}}
    ]
  }
}
```

Preview дополнительно принимает `window_start_utc` и `time_basis`:
`availability_at` либо явно выбранный `backend_processed_at_historical`.
Create добавляет `name` и `rule_hash`, полученный при проверке. Один ключ с тем
же телом возвращает прежний UUID; другое тело с тем же ключом получает 409.
Сам хэш — SHA-256 канонического JSON с сохранением порядка признаков.

## Каталог операций

`/operators` сохраняет прежние поля и публикует `compatible_fields` (точные
пары ECS-type/is_array), `arity`, обязательные `parameters`, их типы, nullable
и вес. `/sources/{id}/fields` дополнительно возвращает допустимые `operators`.
Неподдержанные поля и вложенные nested/flattened имеют явную причину.
Имена полей берутся только из поставляемого ECS 9.4.0. Поддержка операции над
типом массива не добавляет отсутствующее в каталоге поле этого типа.

Скалярные типы: keyword, constant_keyword, wildcard, text, match_only_text,
boolean, long/integer/short/byte, float/double/scaled_float, date, ip.
Числа конечны, целые проверяются по разрядности и JSON-форме (1.0 не long).
Даты — ISO `YYYY-MM-DDTHH:mm:ss[.ffffff]Z` или с явным
`±HH:mm[:ss[.ffffff]]`, включая однозначный выход действующего нормализатора
`1900-01-01T00:00:00+05:21:10`. Календарная дата и смещение проверяются;
сравнение и ключи частот определяются абсолютным UTC-моментом, включая DST-fold.
SQL явно трактует локальную часть как UTC и вычитает проверенный interval
смещения, поэтому секунды/микросекунды смещения не теряются и TimeZone сессии
не участвует в разборе. Все casts защищены CASE. IP — отдельный IPv4/IPv6
без маски и zone ID.

Технический диапазон date-операций — абсолютные моменты от
`0001-01-01T00:00:00Z` до `9999-12-31T23:59:59.999999Z` включительно.
Проверяется итог после вычитания смещения, а не год локальной записи.
Литералы за границами дают адресный `422 / invalid_literal_type` по пути
условия/значения; например, `0001-01-01T00:00:00+01:00` отклоняется до SQL.
Сохранённая дата вне диапазона даёт `invalid_input_type`, null и invalid_count
у затронутого признака по прежней политике качества. Рабочая точка с причиной
сохраняется вместе с курсором, само значение не вызывает транспортный retry.
Это распространяется и на элементы date-массивов.

Внутри SQL date-значения передаются как `timestamp without time zone` с
техническим смыслом UTC; адаптер явно добавляет метку UTC после чтения.
Так край диапазона не превращается в BC/год 10000 из-за TimeZone драйвера.
Это не настройка TimeZone сессии и не подмена значения: сравнения, частоты
и границы ECS `@timestamp` используют те же абсолютные моменты. Ключи категорий
остаются в чистой логике `aggregation/`. Нормализатор, события и сохранённые
точки не переписываются.

| Условие | Аргументы и смысл | Вес |
| --- | --- | --- |
| `all`, `any` | args из одного или более условий | 1 |
| `not` | ровно одно условие в args | 1 |
| `eq`, `neq` | scalar field, строго типизированный value | 1 |
| `in`, `not_in` | scalar field, непустой однородный список value | 1 |
| `exists`, `not_exists` | scalar/typed-array field, без value | 1 |
| `gt`, `gte`, `lt`, `lte` | число или date, один value | 1 |
| `between` | число или date, два упорядоченных value, обе границы включены | 1 |
| `contains`, `starts_with` | строка, непустой буквальный value с учётом регистра | 2 |
| `in_cidr` | scalar ip, IPv4/IPv6 CIDR value; другая семья не совпадает | 2 |
| `has_any` | typed-array, непустой однородный список value; хотя бы один элемент | 1 |
| `has_all`, `has_none` | typed-array, все / ни одного элемента из value | 2 |

`neq`/`not_in` требуют присутствующего ненулевого значения. `not` может
совпасть с отсутствием/null, но никогда с ошибкой типа дочернего условия.
Ошибки всех дочерних условий сохраняются независимо от короткого замыкания.
Пустая строка и пустой массив присутствуют. Пустой массив даёт false для
has_any/has_all и true для has_none; отсутствующий/null не совпадает ни с одним
has-условием. Неоднородный массив, null/объект/массив внутри него — неверный тип.
Массивы допускают те же скалярные типы элементов; скалярные операции массив
не принимают. Строки `%`, `_`, кавычки, обратный слеш и Unicode буквальны.

| Базовый признак | Поле / результат | Вес |
| --- | --- | --- |
| `count` | без поля, число выбранных записей | 1 |
| `distinct_count` | scalar, точное число уникальных присутствующих значений | 8 |
| `sum`, `avg`, `min`, `max` | число, сумма/среднее/минимум/максимум | 2 |
| `present_count`, `missing_count` | scalar/typed-array, наличие правильного типа / отсутствие или null | 1 |
| `true_count`, `false_count` | scalar boolean, число true / false | 1 |
| `range` | число, max − min | 4 |
| `variance`, `stddev` | число, генеральная дисперсия (делитель N) / её корень | 4 |
| `median`, `percentile` | число, непрерывный квантиль полного набора | 12 |
| `mode_count`, `mode_share` | scalar, частота моды / её доля среди присутствующих значений | 12 |
| `derive` | выражение expr | 0 |

Только percentile требует дополнительный параметр `percentile` от 0 до 1;
median равна percentile 0.5. Для отсортированного набора размера N позиция
`p*(N-1)`, между соседними значениями — линейная интерполяция. Входные long
не преобразуются в binary64: SQL сохраняет numeric, интерполяция — Decimal
с точностью 100 десятичных цифр. Целый результат возвращается JSON integer
без потери int64; дробный результат API округляется до ближайшего binary64
при преобразовании Decimal в float (включая дроби рядом с границей int64).
Это округление представления, а не выборочное приближение квантиля.
variance/stddev используют PostgreSQL numeric population statistics; возможна
разница последнего разряда с вычислением binary64.

На пустом наборе count/distinct/present/missing/true/false равны 0;
остальные статистики, включая частоту и долю моды, дают null/no_values.
При одном числе range/variance/stddev равны 0. Категория моды не сохраняется;
ничья частот не меняет числовой результат. valid_count у четырёх новых
счётчиков — число записей соответствующего подсчёта, у моды — знаменатель.

Производные выражения используют только ссылки на ранее объявленные признаки
`{"ref":"key"}` и числовые константы `{"value":2}`. Вес каждого узла — 1.
Бинарные add/subtract/multiply/divide и ratio (синоним divide) имеют два args;
percent, per_second, abs — один; clamp — три (значение, нижняя и верхняя
границы); min_of/max_of — два или более. percent умножает долю на 100,
per_second делит на сохранённую длительность окна, abs берёт модуль,
clamp ограничивает замкнутым диапазоном, min_of/max_of выбирают экстремум.
Обратные границы clamp дают `invalid_clamp_bounds`. Прежние коды причин
сохранены; нулевой ratio имеет `division_by_zero`.

Пример дополнительных признаков:

```json
{
  "where": {"op":"in_cidr","field":"source.ip","value":"192.0.2.0/24"},
  "features": [
    {"key":"p95","name":"95-й перцентиль байтов","op":"percentile","field":"network.bytes","percentile":0.95},
    {"key":"share","name":"Доля частого метода","op":"mode_share","field":"http.request.method"},
    {"key":"percent","name":"Процент","op":"derive","expr":{"op":"percent","args":[{"ref":"share"}]}}
  ]
}
```

Каждый результат содержит `value`, `reason`, `valid_count`, `invalid_count`.
Для базовых признаков счётчики относятся к участвующим записям; для производных
`valid_count=1` при успешном вычислении, иначе `invalid_count=1`.
Отсутствие поля и JSON null не заменяются нулём. Неверный тип, включая
неоднородный массив в условии, отравляет затронутый признак с
`invalid_input_type`. Пустые числовые статистики имеют `no_values`, деление
на ноль — `division_by_zero`, отсутствующий операнд — `missing_operand`,
переполнение — `non_finite_result`. Ноль count/distinct сам по себе не
доказывает полноту покрытия.
Защитная проверка нечислового/не конечного операнда использует отдельные
`non_numeric_operand`/`non_finite_operand`; преобразование строки в число не выполняется.

## Время и атомарность

Рабочее окно определяется сохранённым UTC-якорем и длительностью 1…604800
секунд. `scheduled_at=end_utc`; часовой пояс используется для ввода и
представления. Первый рабочий start не раньше времени создания.
Постоянный `aggregate-worker` в обоих Compose-режимах ждёт миграций и здорового
WAL-декодера. Окно закрывается только после материализации барьера TASK-30;
вход выбирается по полуоткрытому интервалу `availability_at`.

Для отдельного перезапуска используйте `restart --no-deps aggregate-worker`
с теми же Compose-файлами и окружением. После `stop` существующий контейнер
запускается через `up -d --no-deps --no-build aggregate-worker`.

Признаки, число событий и границы ECS `@timestamp` читаются одним SQL statement.
Полная точка и следующий индекс сохраняются одной транзакцией под блокировкой
расписания. Ошибка/timeout откатывает обе записи; worker сохраняет безопасную
диагностику и повторяет расчёт с ограниченным backoff. Остальные агрегаты
продолжают обрабатываться. После простоя активные окна восполняются по порядку.
Один worker выполняет не более четырёх независимых расчётов одновременно;
бюджет плана не является глобальным ограничителем памяти всех worker и БД.
Архивирование, возобновление, исторический расчёт и удаление берут ту же
блокировку расписания; барьер не разрешает запись после удаления.
Удаление в том же UnitOfWork блокирует связанных детекторов в порядке UUID,
останавливает их и повышает revision. Состояния моделей, входы прогрева,
working outcomes и findings сохраняются. Кандидат, рассчитанный до удаления,
не может подтвердиться после него. Архивирование сохраняет модель;
намеренный диапазон пропуска после resume не оценивается детектором.

Исторический запрос не двигает рабочий курсор. Окно должно быть выровнено и
закончиться не позже создания агрегата. Повтор возвращает неизменяемую точку.
Для availability-истории используется отдельный долговечно материализованный
барьер. Preview не создаёт барьер. Без уже сохранённых барьера и доказательств
покрытия он помечается `unverified`: сам снимок не доказывает полного покрытия.

## Обновление capture

Перед первым bootstrap и перед обновлением существующей установки остановите
все старые API/consumer/writer-процессы, worker агрегатов и WAL-декодер. Затем выполните миграции, bootstrap,
дождитесь готовности декодера и запускайте обновлённые API/worker. Не запускайте
две версии writer одновременно.
Bootstrap отказывает при обнаружении активной записи/блокировки writer на
источниках или событиях. После bootstrap отложенный constraint trigger проверяет
наличие маркера у каждой новой записи в момент commit и отклоняет старый writer
без маркера. Это дополнительная защита к обязательной остановке старых процессов.

Первая инициализация без прежнего прогресса/маркеров сохраняет одним действием
`legacy_cutover_at` и `availability_verified_from_at` по времени БД. Повторный
bootstrap их не сдвигает. Для прежней установки первая граница остаётся NULL;
новый upgrade-барьер даёт только будущую консервативную границу после
материализации. Даты не восстанавливаются из heartbeat, LSN или ручного ввода.

Сохраняемая старая история разрешена только до известного `legacy_cutover_at`
и только по записям без маркера. Availability-история разрешена только начиная с
`availability_verified_from_at`; markerless-запись в таком окне вызывает отказ.
Пересечение границ или неизвестная область дают `historical_time_basis_unknown`.
Явный ретроспективный preview по времени обработки остаётся read-only и
`unverified`, в том числе для старой установки с неизвестной первой границей.

## Ресурсные границы

Стартовые значения задаёт `Limits`; каждое можно конфигурировать переменной
`AGGREGATE_<ИМЯ_ПОЛЯ_В_ВЕРХНЕМ_РЕГИСТРЕ>` в окружении API и worker одинаково.
`work_mem_mb` не может превышать 32. Порог в пять признаков отсутствует.

| Поле | Значение |
| --- | --- |
| `json_bytes` | 65536 |
| `depth` | 8 |
| `literals` | 256 |
| `preview_rows` | 100000, без усечения |
| `cost` | 50000000 |
| `preview_timeout_ms` | 10000 на SQL statement |
| `working_timeout_ms` | 30000 на SQL statement |
| `work_mem_mb` | 32 на операцию плана |
| `total_memory_mb` | 256, отдельная оценка совокупной памяти |
| `array_elements` | 4096 элементов одного сохранённого массива, без усечения |

Стоимость — `estimated_rows * sum(operator_weight)`: count и узел условия = 1,
числовая статистика = 2, exact distinct = 8, узел арифметического выражения = 1.
Веса расширенных операций приведены в каталоге выше; прежние веса сохранены.
Для `has_all` и `has_none` эффективный вес одного условия — `2 * len(value)`:
компилятор выполняет отдельное типизированное EXISTS-сканирование для каждого
литерала. Для `has_any` над новыми типами элементов вес — `len(value)`.
Для прежних keyword/constant_keyword-массивов `has_any` сохраняет принятый вес 1.
Размер списка считается до какой-либо дедупликации; лимит 256 и отсутствие
усечения сохраняются. Формула опубликована в `weight_formula` каталога.
Например, count + has_none при 1 строке шириной 22000 байт дают стоимость
`(1 + 2*L) * ceil(22000/256)`: 258 при L=1 и 44118 при L=256.
Превышение лимита даёт `resource_budget_exceeded`, фактор `operator_cost`;
следует сократить список, окно или сложность правила. Частичная точка и
продвижение курсора при таком отказе не сохраняются.
Для правил с новыми операциями или новыми поддержанными типами стоимость
дополнительно умножается на `ceil(row_width/256)`: длинные строки и массивы
не оцениваются как короткий скаляр. Для них же резервируются `4*row_width`
байт временной памяти при непустом входе. Прежние оценки старых правил сохранены.
Общее where расширенного правила материализуется один раз в том же SQL-снимке;
его буфер дополнительно учитывается как `min(rows*(row_width+16), work_mem_bytes)`.
Это исключает повторение сложного предиката в каждой колонке статистики;
избыток tuplestore PostgreSQL может вынести на диск в рамках timeout.
Оценка совокупной памяти — `(distinct_features + 4 * materialized_features) * rows * row_width + vector_width * 1024`
байт; `row_width=max(256, max(octet_length(ecs_data::text))+64)` по выбранному окну.
materialized_features — число median/percentile/mode_count/mode_share: учитываются
полные массивы SQL, значения драйвера и Python sort/Counter, а не только work_mem.
Большие строки и массивы входят в row_width; память частот оценивается по
верхней границе кардинальности rows. Превышение array_elements возвращает
resource_budget_exceeded с фактором array_elements и именем переменной
AGGREGATE_ARRAY_ELEMENTS. Ни точка, ни частичный ответ не сохраняются.
Это консервативная стартовая оценка несжатого состояния, а не гарантия
пикового потребления PostgreSQL. Кардинальность оценивается верхней границей по
числу строк. API также показывает общий объём источника и предварительную
оценку RCF `vector_width * 100 * 256 * 8` байт; конкретные параметры детектора
будут проверяться при его создании. Runtime-ошибки и отставание остаются видимы.
Timeout в 30 секунд не обещает своевременность секундного окна при любом потоке.
Сервис устанавливает `SET LOCAL jit=off` вместе с timeout/work_mem только в
транзакции расчёта: сложные защищённые JSON-выражения не должны тратить время
секундного окна на компиляцию сотен LLVM-функций. Настройка всей БД не меняется.
SQL-план отдельно проверяется на предел PostgreSQL в 1664 выходные колонки:
текущая компиляция использует `5 + 3 * число_базовых_признаков`. Размер массива
и ширина строки передаются одной внутренней колонкой, чтобы сохранить прежнюю
допустимую ширину SQL-плана. Ошибка
`statement_width` предлагает разделить базовые признаки между агрегатами.
Это ограничение конкретного SQL-плана; производные признаки не добавляют ему
колонок, и самостоятельного фиксированного лимита ширины вектора нет.
