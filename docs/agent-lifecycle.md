# Жизненный цикл Fluent Bit-агентов (TASK-20)

В development и production управление агентами выполняется через существующий FastAPI. Kafka admin credentials доступны только отдельному закрытому Compose-сервису `provisioner`; у него нет опубликованных портов. API и consumers используют runtime reader без прав изменения топиков, SCRAM credentials и ACL. В production provisioner соединяется с Kafka по `SASL_SSL`, проверяя CA и имя узла.

## Секреты и запуск

В development Compose использует `AGENT_CREDENTIALS_KEY_FILE`, по умолчанию `.dev/agent_credentials_key`. Создайте постоянный Fernet key командой `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` и сохраните его в этот файл с правами только для владельца. Не меняйте ключ, пока в БД есть невыданные credentials. Файл исключён из Git. В production задайте `AGENT_CREDENTIALS_KEY_FILE` на защищённый файл хоста, смонтированный как Docker secret только в API и provisioner.

Provisioner получает `KAFKA_ADMIN_USERNAME`, `KAFKA_ADMIN_PASSWORD_FILE`, runtime reader и ключ шифрования. Перед запуском проверьте права на файлы секретов и доступность Kafka. У API не должно быть `KAFKA_ADMIN_PASSWORD_FILE` или секрета `kafka_admin_password`.

## Состояния и операции

- `provisioning` — ожидается или выполняется операция Kafka. Состояние операции доступно через `GET /api/v1/agents/{id}/operations/{operation_id}`.
- `ready` — credentials и точечные ACL подтверждены Kafka; назначения привязаны к проверенным topic ID.
- `error` — операция требует восстановления или проверки администратором. API показывает безопасное сообщение; исходные исключения Kafka и credentials не возвращаются.
- `revocation_pending` у назначения — обнаружено новое поколение topic, отзыв ACL ещё не подтверждён. Provisioner повторяет отзыв после восстановления Kafka; имя остаётся зарезервированным.
- `revocation_pending` — Kafka ещё не подтвердила полный отзыв. Назначения сохраняют резервирование.
- `revoked` — ACL и SCRAM identity отозваны. Сам Kafka topic, source, события и offsets сохраняются.

Агент сохраняет идентичность кластера и административное подключение после снятия последнего назначения. Полный отзыв проверяет удаление ACL и SCRAM credentials каждой известной ревизии даже при пустом списке топиков. Если Kafka недоступна, агент остаётся в `revocation_pending`, а операция повторяется; уже удалённый principal считается подтверждённо отозванным. После подтверждённого отзыва маршрут освобождается, а идентичность кластера остаётся в истории агента. Миграция `0012_agent_cluster_route` переносит маршрут из исходной операции регистрации, включая агентов без назначений.

Регистрация и добавление назначения принимают действие `create` или `attach`. `create` создаёт топик с тремя partitions и replication factor 1; если имя неожиданно уже занято, операция завершается конфликтом и требует сверки. `attach` проверяет существование топика, его ID и кластер. Создаваемый source выключен и не получает нормализатор. При подключении к существующему source его настройки и позиция чтения сохраняются.

Изменяющие запросы используют UUID-заголовок `Idempotency-Key`. Изменение имени/описания выполняется через `PATCH /api/v1/agents/{id}`. Для топиков используются `POST /api/v1/agents/{id}/topics` и `DELETE /api/v1/agents/{id}/topics/{assignment_id}`; отзыв выполняется через `POST /api/v1/agents/{id}/revoke`, перевыпуск — через `POST /api/v1/agents/{id}/credentials/rotate`.

Ключ закрепляется за действием, агентом и содержимым запроса: точный повтор возвращает прежнюю операцию, другое действие или тело получает `409 idempotency_key_conflict`. `PATCH` остаётся обычным обновлением без устойчивого Kafka-задания.

Перевыпуск сразу отзывает предыдущую ревизию, поэтому агент приостанавливают до установки новых credentials. После успешной операции новые данные получают один раз через `POST /api/v1/agents/{id}/credentials/claim`. Ответ содержит `Cache-Control: no-store`; пароль не включается в карточку или список. Повторное получение после выдачи невозможно. Если ответ потерян или пароль утрачен, создайте явный запрос на перевыпуск.

## Восстановление

Provisioner хранит операции в `app.kafka_provisioning_operations`, повторяет временные сбои ограниченное число раз и подбирает просроченные `running` операции после рестарта. Пока прежний исполнитель удерживает блокировку, второй не получает то же задание. Идентичность каждого созданного топика записывается до выдачи ACL; подтверждённый topic ID проверяется при повторе, а создание не повторяется. Kafka не хранит пользовательскую отметку о том, кто создал топик: если процесс остановился после запроса создания до фиксации topic ID, одно существующее имя не доказывает принадлежность операции. Provisioner отзывает доступ, оставляет топик и source, освобождает назначение лишь после подтверждённой очистки и помечает операцию `failed`. Оператор сверяет topic ID и регистрирует нового агента с `attach` либо выбирает другое имя; прежнего ошибочного агента можно явно отозвать. Если Kafka недоступна при очистке, резервирование сохраняется до её подтверждения.

При смене Kafka topic ID provisioner переводит назначение в `revocation_pending` и повторяет отзыв точного ACL при каждом проходе и после рестарта. Только после подтверждения отзыва оно переходит в `error`; имя остаётся зарезервированным до решения администратора. Не удаляйте source и Kafka topic ради восстановления. Если credentials были выданы, но ответ клиенту потерян, пароль не восстанавливается; используйте ротацию.

## Управление через интерфейс

Администратор открывает «Обработка данных → Агенты», задаёт имя и от 1 до 50 топиков. Для нового топика выбирается «Создать», для существующего свободного — «Закрепить». Наличие топика в выпадающем списке не гарантирует доступность к моменту выполнения: окончательная проверка происходит на сервере. Операция сначала получает статус «Настройка Kafka». Дождитесь «Доступ готов»; этот статус подтверждает Kafka credentials и ACL, но не означает, что процесс Fluent Bit запущен или отправляет данные.

В карточке доступны редактирование названия и описания, добавление и снятие топика, перевыпуск и полный отзыв. Снятие назначения и отзыв не удаляют топики, источники и события. После регистрации источник выключен и не имеет нормализатора. Назначьте нормализатор и включите его в разделе «Источники», затем проверяйте поступление в разделе «События».

После готовности нажмите **«Получить конфигурацию»**. Это отдельное одноразовое действие. Сразу скачайте `fluent-bit.conf` и, при TLS с частным CA, `diploma-kafka-ca.pem`. Конфиг содержит пароль; не отправляйте его в чаты и журналы, храните с правами только владельца (например, `chmod 600 fluent-bit.conf`). Пароль не появится повторно после закрытия окна или ухода со страницы. При потере конфигурации выполните явный перевыпуск; прежний доступ после него прекращается, пока вы не установите новый конфиг.

В каждом блоке `[INPUT]` замените `Path /REPLACE/WITH/SERVICE_N.log` на путь к файлу конкретной службы **на хосте агента**. Не меняйте пары `Tag` и `Match`: отдельный `[OUTPUT]` отправляет эту службу только в назначенный топик. Tail создаёт поле `log`, Kafka output добавляет `timestamp` в ISO 8601; это ожидаемый конверт `{timestamp, log}`. Конфиг проверен на Fluent Bit 4.2.3; установите эту версию и запускайте её с полученным файлом. Для production разместите CA рядом с конфигом по пути `/etc/fluent-bit/diploma-kafka-ca.pem` или скорректируйте `rdkafka.ssl.ca.location` на фактический путь. Установите ограниченные права и на CA-файл. Брокер должен быть доступен по внешнему адресу из конфига, а его сертификат должен соответствовать DNS-имени. TLS и проверку имени не отключайте. Локальный development-профиль использует loopback `SASL_PLAINTEXT` только для тестовых данных; для удалённого агента нужен production-подобный TLS-профиль.

При отсутствии событий проверьте путь входного файла и права Fluent Bit на чтение, достижимость внешнего Kafka-адреса, затем Kafka metadata, TLS/CA/имя, SCRAM и ACL. Убедитесь, что агент и назначение в состоянии `ready`, а источник в разделе «Источники» включён и имеет готовый нормализатор. Если выдача пароля завершилась на сервере, но ответ потерялся, повторная выдача невозможна: обновите состояние и выполните перевыпуск.

`GET /api/v1/agents/transport` (только `agents.write`) возвращает опубликованный Kafka listener, транспорт и публичный CA без Kafka admin/runtime-reader credentials. Ответ имеет `Cache-Control: no-store`. Адрес берётся из `KAFKA_AGENT_PUBLIC_HOST` и `KAFKA_AGENT_PUBLIC_PORT`, согласованных с опубликованным listener Compose, а не из внутреннего `kafka:9092`.
