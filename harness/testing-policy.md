# Политика тестирования приложения

Обязательное приложение к `AGENTS.md` для всех ролей. Команды существующего контура — в [профилях](../docs/agent-test-profiles.md), изоляция и очистка — в [resource-policy.md](resource-policy.md). Правило выбора по затронутым компонентам действует также для текущих TASK/FIX: прежнее требование всего приложения перед каждым коммитом заменено этим документом. Продуктовые цели и критерии этапа этим не меняются.

## 1. Как определить объём проверок

- **Исполнитель:** адресные проверки изменённого поведения и затронутых предметных областей.
- **Этапный архитектор:** независимое ревью и полные наборы только затронутых крупных компонентов: backend, frontend, Kafka/ingest, PostgreSQL/WAL, ML/worker, поставка, проверочный контур. Неизменённые компоненты без затронутых контрактов не включаются в ревью или предкоммитный прогон.
- Влияние определяется diff, контрактами и реальными потребителями. Изменение общего response/error/auth-контракта или proxy-маршрута может затронуть frontend без правок его папки. Внутреннее изменение backend либо новый API, который существующий UI не использует, само по себе frontend не затрагивает.
- Наличие PostgreSQL, Kafka, API или frontend на тестовом стенде не делает их затронутыми компонентами. Служебные зависимости можно поднять для выбранной проверки; запуск их собственных полных наборов из этого не следует. Изменение одного файла runner/Compose не означает изменение всех его веток и сервисов.
- Перед запуском Этапный архитектор кратко фиксирует выбранные компоненты, причину влияния и необходимые интеграционные связи. Если влияние неясно, изучает зависимости; нельзя автоматически выбирать всё приложение «на всякий случай».
- Каждый фикс требует регрессионного теста и проверки исправляемого сценария. Запрещено ослаблять проверки ради успеха. Полный набор всего приложения требуется при приёмке этапа/релиза; в задаче он возникает только при фактическом влиянии на все компоненты либо по прямому указанию человека.
- Этапный архитектор приводит проверки активных TASK/FIX в соответствие с этой политикой до продолжения ревью/коммита. Исполнитель не переписывает спецификацию самостоятельно. Подтверждённый дефект, обнаруженный прежним широким прогоном, сохраняется в учёте: Этапный архитектор определяет его связь с текущей задачей или отдельную доработку; сама смена политики не принимает задачу и не отменяет фикс.

## 2. Исполнитель

Проверяет изменённое поведение, его граничные случаи и конкретные зависимости адресными unit/component, сервисными, DB/контрактными или интеграционными тестами. При изменении запуска проверяет затронутый режим/сценарий. Не запускает полный компонентный набор или всё приложение только потому, что существует общий профиль. Общая статическая проверка допустима, если инструмент нельзя корректно ограничить затронутой областью.

В отчёте указывает области, команды, результаты и ограничения. После выполнения [критериев готовности](workflow.md#5-критерии-готовности-исполнителя) сообщает «готово к ревью»; это не приёмка задачи. Результаты Исполнителя не подменяют независимые проверки Этапного архитектора.

## 3. Этапный архитектор: ревью, проверки компонентов и коммит

1. После сигнала человека проверяет требования, код и архитектуру по [правилам ревью](workflow.md#6-ревью-задач-и-этапов), определяет компоненты и нужные связи. Для диагностики и подтверждения исправлений выполняет необходимые адресные проверки; не обязан сначала прогнать целый компонент и затем повторить его перед коммитом.
2. При дефекте оформляет `FIX-TASK`. После исправления и нового сигнала человека повторяет ревью затронутого решения. Подтверждённый инфраструктурный сбой диагностирует отдельно от дефекта продукта.
3. Успех ревью означает **«ревью пройдено; задача не принята, ожидает проверок компонентов и коммита»**.
4. На итоговом варианте независимо выполняет **полные наборы выбранных крупных компонентов** и необходимые интеграции/smoke. Полный набор каждого компонента достаточно выполнить один раз: успешный независимый запуск при ревью засчитывается перед коммитом, если его код, тесты, зависимости, конфигурация и подготовка данных по-прежнему соответствуют итоговому варианту. Смена названия фазы не требует второго одинакового прогона.
5. После FIX заново определяет влияние и повторяет полные наборы изменённых исправлением компонентов и затронутые связи. Успешные независимые результаты остальных неизменившихся компонентов сохраняются с указанием основания применимости. Изменение общего helper/fixture учитывается для тех проверок, которые реально используют изменённый путь. При инфраструктурном отказе повторяется непрошедший обязательный набор/профиль, а не всё приложение.
6. После успешных обязательных проверок, очистки ресурсов и сверки итогового diff записывает результат в план и создаёт коммит. **Задача принята только после успешного коммита**; до этого следующая не выдаётся. Непройденная обязательная проверка выбранного компонента блокирует коммит.

Результат относится к проверенному варианту соответствующего компонента, его окружению и входам. Если они изменились, связанные проверки теряют применимость; результаты незатронутых компонентов автоматически не аннулируются. Дополнение плана/отчёта фактическими результатами без изменения исполняемого кода и контура не требует нового прогона приложения. Набор с падением не становится успешным по одному адресному повтору: нужно диагностировать отказ и успешно завершить обязательный набор этого компонента/профиля.

Запись в плане может указывать: «Ревью и обязательные проверки затронутых компонентов пройдены; задача принимается после успешного коммита». После коммита Этапный архитектор сообщает его хэш человеку; для внесения хэша не нужен отдельный административный коммит. Таблица принятых страниц подготавливается в тот же коммит.

## 4. Компоненты, интеграции и smoke

Полный набор компонента означает весь постоянный набор этого компонента, а не несколько тестов выбранной функции. Состав и селекция существующих профилей описаны в [инструкции контура](../docs/agent-test-profiles.md).

| Компонент | Когда включать и что проверяет Этапный архитектор |
| --- | --- |
| Backend | Изменены серверные сценарии, репозитории, модели или общая серверная инфраструктура: полный broker-independent `backend-db`. Если затронут также Kafka/ingest, полный `kafka-integration` покрывает этот backend-набор; не повторять его отдельно |
| Frontend | Изменены клиентские код/сборка/зависимости или реально потребляемый существующим UI контракт: полный `frontend` (типы, lint, формат, Vitest, сборка), стандартные браузерные сценарии компонента и необходимые live-связи. Не включать только из-за внутреннего backend-изменения |
| Kafka/ingest | Изменены broker/listeners/SCRAM/ACL, consumer, offsets/recovery, протокол доставки или provisioning: полный Kafka-интеграционный набор и metadata. Если backend не менялся, допустима селекция всего Kafka-набора через `--pytest`, без повторения остальных серверных тестов |
| PostgreSQL/WAL | Изменены схема/constraints/хранение: миграции, схема и DB-контракты. WAL/pgoutput gate обязателен при влиянии на capture, writer, барьеры или репликацию; произвольная миграция другой подсистемы не требует его автоматически. Уже покрытые backend/ML-профилем проверки не дублировать |
| ML/детекторы | Изменены detection, прогрев, checkpoint, worker или целевой runtime/JRE/JAR: полный целевой `backend-db --rcf` с постоянными runtime/worker-тестами. Обычный backend discovery его не заменяет |
| Поставка и proxy | Изменены Dockerfile/Compose, запуск, health или lifecycle: smoke затронутых сервисов и режимов. Общие маршруты/TLS/auth проверять по влиянию. Добавление worker в обе поставки требует worker-проверок dev/prod, но не frontend unit/browser/OIDC/TLS-agent автоматически |
| Проверочный контур | Изменены prepare/cleanup/fixture/helper или ветка runner: постоянные тесты контура и затронутые профили. Одна изменённая ветка монолитного runner не требует всех остальных профилей |
| Документация | Только тексты/ссылки: согласованность требований, ссылки и diff; наборы приложения не запускаются |

Сквозные сценарии выбираются по изменённому пути: локальная доставка, внешнее чтение, агрегаты, detector-worker, UI или сессия. Worker-задача без изменения внешнего чтения не требует `external-end-to-end`; исправление его fixture уже затрагивает этот профиль и требует проверки именно его. Исправление внешней fixture само по себе не требует всего frontend Vitest или повторения неизменённой ML-логики.

Полные standard development/production smoke не обязательны перед каждым коммитом. Для задачи выбираются режимы и сценарии по влиянию; адресный `--detector-only` может быть достаточным для затронутой поставки worker. Он не доказывает прохождение UI/OIDC/TLS-сценариев, когда они действительно нужны. При изменении общих настроек поставки проверяются все зависимые сервисы/режимы, без автоматического добавления тестов незатронутых компонентов.

Используется единый постоянный контур. Если существующая команда без необходимости запускает посторонние проверки или собирает лишние сервисы, выбирать подходящую селекцию либо минимально доработать существующий профиль в рамках активной задачи; не создавать отдельную архитектуру стенда и не считать удобство широкой команды основанием для лишнего прогона. Фактические ограничения текущего `--detector-only` описаны в инструкции профилей.

## 5. Приёмка этапа Главным архитектором

При завершении этапа или финальной приёмке релиза выполняются полный регрессионный прогон всех компонентов и согласованные сквозные сценарии. Главный архитектор при ревью этапа самостоятельно запускает полный набор проверок всего приложения и согласованные сквозные сценарии на том же постоянном контуре; прежние отчёты не выдаются за его новые запуски. Дополнительные проверки, например нагрузочные испытания, выполняются по согласованию с человеком. Порядок передачи и решения по этапу описан в [workflow.md](workflow.md#передача-и-ревью-этапа).

## 6. Воспроизводимые профили интеграционных проверок

- Исполнитель и Этапный архитектор используют **один постоянный проверочный контур проекта**: одни и те же Compose-файлы, сценарии/команды, зафиксированные версии образов и подготовку данных. Не собирать отдельную архитектуру стенда для роли или задачи. Разрешены только уникальные идентификаторы прогона, свободные порты и тестовые секреты. Если постоянного сценария для обязательной проверки ещё нет, создать его в рамках активной задачи как повторяемый инструмент с инструкцией запуска и очистки; Этапный архитектор проверяет именно этот сценарий и его изоляцию. Главный архитектор при ревью этапа использует тот же контур.
- Перед прогоном явно назвать профиль: `frontend` (локальные frontend-проверки), `backend-db` (backend и тестовая PostgreSQL, в том числе варианты `--rcf` и `--wal`), `kafka-integration` (реальный брокер с SCRAM/ACL), `end-to-end` (полный собственный путь через proxy/Fluent Bit/Kafka/PostgreSQL/UI), `external-end-to-end` (внешний индексер и UI), `smoke-development` или `smoke-production`. У каждого профиля в отчёте фиксировать команду, версии ключевых образов, имя Compose-проекта, адреса/порты без паролей, имена переменных окружения, результаты и причину пропуска. Успех одного профиля не подменяет другой.
- Для Kafka-тестов выбрать **один** изолированный брокер данного прогона. До запуска сверить, что bootstrap-адрес, опубликованный порт и `advertised.listeners` указывают на тот же брокер и достижимы из каждой среды клиента: с хоста — внешний listener, из API/consumer-контейнера — внутренний listener, из тестового агента — предназначенный ему внешний listener. Эти адреса могут различаться, но Kafka cluster ID должен совпадать. Не записывать внешний `localhost`-адрес как подключение API внутри контейнера. Проверить metadata после bootstrap из каждой среды и только затем запускать тесты. Нельзя молча использовать работающий `diploma` или подменять неудачный порт/протокол другим брокером.
- Профиль Kafka должен задавать согласованный набор `KAFKA_TEST_*` (адрес, протокол, reader/admin credentials files, CA и допустимые dev-адреса) и `TEST_DATABASE_URL` одной изолированной тестовой БД. Интеграционные тесты не должны обращаться к жёстко заданному `localhost:9092` или другому адресу вне этого профиля; исключения для тестирования отказа должны быть явными. При обнаружении такого теста исправить тестовый контракт в рамках относящегося к нему фикса, а не подгонять стенд или объявлять продукт неисправным без диагностики.
- Если набор упал на подключении, отдельно зафиксировать: DNS/маршрут до broker, metadata с advertised address, TLS/CA/hostname, SCRAM, ACL и доступность PostgreSQL. Не выдавать инфраструктурный сбой за регрессию продукта и не объявлять приёмку успешной до повторного прогона обязательного сценария. Повторяемый сквозной сценарий оформлять как постоянный тест/скрипт с документированной подготовкой; одноразовые исследовательские файлы в репозиторий не добавлять.

- Для выбранных smoke по-прежнему проверять resolved Compose, изоляцию и запуск затронутых обязательных сервисов, их HTTP(S)/health и требуемые сценарии восстановления. Проверка UI/React через HTTPS обязательна, когда затронут этот пользовательский путь или выполняется полная приёмка этапа; историческое введение production UI с TASK-26 не является требованием прогонять UI на каждой серверной задаче. Использовать синтетические секреты/данные; не рабочие dev/prod-тома. Неуспех обязательного сценария выбранной поставки блокирует коммит до диагностики/исправления и успешной перепроверки. Результаты и очистка фиксируются в отчёте.

## 7. Единая политика тестовой PostgreSQL

- `diploma_db` — база разработки; тесты и откаты миграций на ней запрещены.
- Обычный полный backend-набор запускается через `backend/scripts/run_tests.py --shared` с `TEST_DATABASE_URL`, указывающим строго на `diploma_test`. Runner пересоздаёт только эту тестовую БД перед прогоном и оставляет её чистой на Alembic head после него. Данные `diploma_test` считаются временными. Профили изолированного контура используют этот же runner в режиме `--temporary`, описанном ниже.
- Для независимого ревью или параллельного запуска использовать `--temporary`: runner создаёт уникальную БД и удаляет её по завершении. Не запускать два набора одновременно на общей `diploma_test`.
- Если тестовая БД помечена revision, но структура не соответствует миграциям, не продолжать тесты на ней и не исправлять revision вручную; пересоздать её штатным runner. Все команды миграций должны использовать URL той же тестовой БД. Не удалять и не пересоздавать базу разработки или другой не названный явно target.

## 8. Отчёт о проверках

Указывать роль/фазу, затронутые крупные компоненты и основание их выбора, адресные или полные наборы, необходимые связи, результаты и пропуски. Кратко пояснять очевидные исключения, например «frontend не изменён, потребляемые им контракты сохранены». Для профилей сохранять реквизиты раздела 6 и результат очистки.

Повторно используемый результат обозначать как прежний независимый запуск Этапного архитектора с основанием применимости, а не как новый прогон. На приёмке всего этапа прежние отчёты не заменяют собственный полный запуск Главного архитектора.

В плане фиксировать результат задачи, статус ревью/приёмки, выбранные компоненты, проверки и ограничения по [правилам ведения плана](workflow.md#8-ведение-плана-этапа). Секреты, одноразовые логи и временные отчёты в Git не добавляются. [Правила очистки](resource-policy.md) действуют на всех фазах, включая неуспех и прерывание.
