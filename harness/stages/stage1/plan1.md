# Этап 1. Конфигурируемый конвейер событий и чтение внешних ECS-источников

## 1. Статус документа

Этот файл описывает согласованный курс этапа 1 и является изменяемым планом. Этапный архитектор вместе с человеком уточняет реализацию и последовательность задач в пределах согласованного результата. Цель, границы и критерии приёмки меняются только после согласования человека с Главным архитектором в порядке, заданном `AGENTS.md`.

План определяет цель, границы и ожидаемый результат этапа, но не заменяет спецификации отдельных задач. Конкретная реализация выполняется только по очередному активному файлу `harness/tasks/TASK-*.md`.

## 2. Исходное состояние

На хостах уже используются агенты Fluent Bit. Агент может собирать логи нескольких служб и отправлять их в Kafka. Для каждого Kafka-источника создаётся отдельный топик, поэтому в рамках собственного конвейера один источник соответствует одному топику.

Сообщение в Kafka имеет входной конверт следующего вида:

```json
{
  "timestamp": "время сбора лога агентом",
  "log": "сырой лог"
}
```

Исходная доставка от источника до Kafka уже работала до начала этапа. На поздней стадии этапа она дополняется управляемой регистрацией Fluent Bit-агентов и правами на топики; само приложение не устанавливает агенты на конечные хосты. Kafka является входной границей собственного конвейера обработки. Дополнительно этап включает чтение уже хранящихся ECS-ориентированных событий из внешнего хранилища без пропуска через этот конвейер.

## 3. Цель этапа

Получить работоспособную первую версию системы, в которой пользователь через веб-интерфейс может:

1. Настроить подключение системы к Kafka.
2. Получить сведения о доступных топиках и выбрать топик как источник событий.
3. Создать и проверить конфигурацию нормализации сырых сообщений этого источника в ECS.
4. Связать источник с конфигурацией нормализации и управлять обработкой.
5. Получать сообщения из Kafka, нормализовывать их и надёжно сохранять в PostgreSQL.
6. Просматривать сохранённые события и результат нормализации.
7. Видеть состояние конвейера и понятные сведения об ошибках получения, нормализации или сохранения.
8. Настроить внешний ECS-ориентированный источник в OpenSearch-совместимом индексере, включая Wazuh 5 как проверочный сценарий, и включать или выключать его доступность в приложении.
9. Выбрать один локальный или внешний источник и исследовать его события в таблице: искать, фильтровать и раскрывать строку для просмотра полей события.
10. Зарегистрировать Fluent Bit-агент, заранее назначить ему топики и получить готовую конфигурацию безопасной отправки без ручного создания его учётной записи и прав Kafka.

Итог этапа — два воспроизводимых пути к одному пользовательскому сценарию просмотра событий: `Kafka → нормализация в ECS → PostgreSQL → API → React-интерфейс` и `внешний индексер → read-only API → React-интерфейс`. Второй путь не переносит события в PostgreSQL и не применяет к ним локальный нормализатор. Оба пути служат фундаментом для последующих аналитических, ML- и LLM-возможностей.

## 4. Зафиксированные технологии и архитектурные решения

- входной брокер сообщений: Kafka;
- агент доставки логов до брокера: Fluent Bit;
- каноническая модель для собственного конвейера: ECS (Elastic Common Schema), зафиксированная на официальном стабильном релизе `9.4.0`; внешние ECS-ориентированные документы читаются без обязательного соответствия этой конкретной версии;
- основная база данных: PostgreSQL;
- бэкенд и HTTP API: FastAPI;
- фронтенд: React с TypeScript;
- управление состоянием фронтенда: MobX;
- единственная библиотека UI-компонентов: Ant Design;
- структура БД изменяется только через версионируемые миграции;
- текущее развёртывание использует один кластер Kafka; сохранённая модель подключений не означает, что два адреса того же кластера образуют два независимых источника;
- один Kafka-источник соответствует одному физическому топику одной службы на одном хосте; общих топиков для нескольких хостов/служб в собственном конвейере нет. Идентичность топика определяется Kafka topic ID, а не только его именем; внешний источник указывает на набор данных внешнего хранилища, например индекс или шаблон индексов;
- общая сущность `source` различает Kafka-источники и внешние источники; настройки подключений и допустимые операции зависят от типа источника;
- топики обнаруживаются непосредственно через Kafka API и не синхронизируются в БД автоматически: запись `source` создаётся только по явному действию пользователя. В будущем сценарии регистрации агента тем же явным действием считается создание агента с назначенными топиками; соответствующие источники регистрируются выключенными;
- новый Kafka-источник создаётся выключенным, может временно не иметь нормализатора и активируется только после назначения корректного нормализатора и проверки доступности подключения и топика; внешний источник не требует нормализатора, а его активация означает доступность чтения через приложение и не изменяет состояние внешнего хранилища;
- внешний доступ проектируется через расширяемый интерфейс адаптера хранилища; в этом этапе реализуется OpenSearch-совместимый адаптер, а Wazuh 5 используется для проверки совместимости, не как единственный разрешённый набор индексов;
- для чтения и поиска событий бэкенд предоставляет общий сервисный интерфейс с реализациями для PostgreSQL и OpenSearch; фронтенд не составляет SQL или OpenSearch Query DSL;
- нормализатор хранит правило как JSONB-объект с версией формата и целочисленную версию самой сущности, автоматически увеличиваемую при изменении; отдельная история версий на этом этапе не ведётся;
- локальная и OIDC-аутентификация должны быть доступны одновременно, а авторизация строится на двух внутренних наборах разрешений с изменяемыми названиями ролей: административном и гостевом read-only;
- локальный и OIDC-вход завершаются единой серверной сессией приложения: браузер получает только непрозрачный случайный идентификатор в защищённой cookie, а сервер хранит его хэш и проверяет актуальные состояние пользователя и разрешения роли;
- OIDC реализуется через Authorization Code Flow; внешний токен используется только на границе входа, не становится сессией приложения и не передаётся React-клиенту;
- слои FastAPI разделяются на HTTP-router, сервисный интерфейс и реализацию, интерфейс репозитория и SQLAlchemy-реализацию; HTTP-слой не содержит запросов к БД и бизнес-правил;
- глобальные настройки приложения хранятся отдельно от пользовательских предпочтений и не содержат открытых секретов;
- удаление Kafka-подключения каскадно удаляет только его Kafka-источники, а удаление внешнего подключения — только связанные внешние источники; прочие зависимые записи сохраняются с обнулением допустимых внешних ключей; удаление подключения не удаляет события во внешнем хранилище;
- сырой вход должен оставаться связан с результатом обработки для диагностики и повторной проверки;
- конкретные библиотеки, формат правил нормализации и прочие компоненты выбираются в задачах только после отдельного архитектурного согласования.
- официальный generated artifact ECS `9.4.0` поставляется вместе с бэкендом и служит серверным каталогом допустимых полей для нормализации и фильтрации локальных событий; runtime-загрузка схемы из Интернета запрещена; каталог доступных полей и типов внешнего источника определяется из его хранилища без отбрасывания дополнительных или префиксных полей;
- подстроковый поиск по сырому логу реализуется средствами PostgreSQL `pg_trgm` с GIN
  trigram index; каталог ECS и этот индекс вводятся вместе с API просмотра событий.
- целевая поставка этапа — один Linux-хост с Docker Compose: PostgreSQL, Kafka, FastAPI и reverse proxy входят в комплект; в TASK-26 production-сборка React включается в тот же комплект и обслуживается через существующий reverse proxy. Контейнеры компонентов управляются одним Compose-проектом, а не объединяются в один универсальный образ;
- браузер использует единый адрес приложения: reverse proxy принимает HTTPS, отдаёт фронтенд и передаёт `/api` в FastAPI. Локальный и OIDC-вход завершаются одной серверной cookie-сессией приложения; OIDC callback использует публичный HTTPS-адрес proxy;
- Fluent Bit отправляет записи напрямую в Kafka, минуя веб-proxy; формат сообщения `{timestamp, log}` сохраняется. После ввода управления агентами топики назначаются до выдачи конфигурации: новые создаёт приложение, существующие можно закрепить только за одним агентом. Агент не получает права создавать произвольные топики; прежнее автосоздание при первой отправке заменяется явным созданием в сценарии регистрации агента. Переход существующей установки к этому режиму должен сохранить накопленные топики и данные;
- аутентификация каждого агента — индивидуальные учётные данные Kafka SASL/SCRAM-SHA-512, авторизация — ACL на назначенные топики. В development и production используются одинаковые сущности агентов, API, UI, управление топиками и права; отличается только транспорт. Для строго локальной разработки с тестовыми данными допускается `SASL_PLAINTEXT` на loopback. Для production и любого удалённого стенда обязателен `SASL_SSL` с проверкой сертификата и имени брокера. Персональные клиентские TLS-сертификаты агентов не требуются;
- внутренние Kafka-клиенты приложения в production получают отдельные от агентов учётные данные и минимальные полномочия для потребления, метаданных и административных действий. Их подключение также защищается и аутентифицируется; служебные секреты не выдаются агентам;
- production-сертификаты и приватные ключи предоставляются защищёнными файлами Linux-хоста только соответствующим контейнерам; их нельзя включать в образы или Git. Внутренние подключения контейнеров не требуют самостоятельных публичных сертификатов.

## 5. Границы этапа

### Входит в этап

- инициализация структуры проекта, бэкенда и фронтенда;
- воспроизводимый запуск необходимых компонентов в среде разработки;
- воспроизводимый Compose-запуск комплектных компонентов на одном Linux-хосте в development и production с защищённой внешней HTTPS-границей и обязательным TLS для внешнего Kafka-канала в production;
- конфигурация подключения к Kafka без постоянного хранения секретов во фронтенде; одноразовая выдача секрета нового агента допускается только в явном административном сценарии;
- одинаковое в development и production управление агентами Fluent Bit через API и UI: регистрация, назначение уникальных топиков, выдача готовой конфигурации, отзыв и перевыпуск доступа; устанавливает агент на хосте сам пользователь;
- персональная аутентификация агентов Kafka, ACL на назначенные топики и защищённый транспорт для production и удалённых стендов;
- одновременная поддержка локального и OIDC-входа с единой внутренней моделью пользователя и разрешений;
- глобальные настройки приложения и будущая страница безопасного управления ими;
- получение метаданных Kafka и списка доступных топиков;
- создание, изменение, просмотр и отключение Kafka-источников и внешних источников;
- конфигурация, предварительная проверка и применение нормализации в ECS;
- управление жизненным циклом обработчиков источников;
- чтение входного конверта из Kafka;
- валидация входного сообщения и времени сбора;
- сохранение сырых данных, ECS-представления и технического происхождения события;
- фиксация и отображение ошибок обработки;
- миграции PostgreSQL и необходимые индексы;
- API для пользовательских сценариев этапа;
- настройка внешних OpenSearch-совместимых подключений, проверка доступа и выбор набора индексов; Wazuh 5 входит как проверочный сценарий, но не ограничивает список допустимых OpenSearch-индексов;
- чтение внешних ECS-ориентированных документов на месте, без локального преобразования в ECS, сохранения в `parsed_logs` или передачи через Kafka;
- общий backend-интерфейс чтения событий с реализациями для PostgreSQL и OpenSearch, серверными поиском и фильтрацией по полям выбранного источника;
- базовая структура приложения React, маршрутизация, MobX-состояние и обработка состояний загрузки и ошибок;
- страницы настройки обоих типов источников и нормализации, контроля работы и просмотра событий;
- автоматические проверки критической логики и сквозного сценария;
- минимальная документация запуска и эксплуатации результата этапа.

### Не входит в этап

- установка и настройка Fluent Bit на конечных хостах;
- ML-модели, построение признаков и поиск аномалий;
- LLM, чат, tool retrieval и граф инструментов;
- автоматический триаж, уведомления и периодические отчёты;
- сложные аналитические дашборды;
- построение, хранение и использование агрегатов, включая снимки полей за временные окна и графики, основанные на таких агрегатах;
- поддержка канонической модели, отличной от ECS;
- адаптеры для внешних хранилищ, отличных от OpenSearch-совместимых индексеров; расширяемый интерфейс для будущих адаптеров входит в этап, но универсальная реализация всех типов хранилищ — нет;
- промышленная оркестрация, горизонтальное масштабирование и высокая доступность;
- универсальная поддержка всех возможных форматов логов без явной конфигурации;
- функциональность, не необходимая для сквозного пользовательского сценария этого этапа.

## 6. Целевая архитектура этапа

### 6.1. Поток управления

После введения управления агентами администратор сначала регистрирует агента и закрепляет за ним несколько конкретных топиков: новые создаёт приложение, существующие проходят проверку уникального владельца. Сервер создаёт персональные учётные данные и Kafka ACL, затем предоставляет готовую конфигурацию Fluent Bit с одноразовой выдачей секрета. Соответствующие Kafka-источники появляются выключенными. Изменение прав, отзыв агента и повторная выдача доступа не удаляют топики или сохранённые события. Старые сообщения существующего топика нельзя задним числом приписать новому агенту. Поскольку операции Kafka и PostgreSQL не составляют общей транзакции, частичное выполнение отражается явным состоянием и подлежит безопасному восстановлению.

1. Пользователь задаёт параметры подключения к Kafka через веб-интерфейс.
2. Бэкенд безопасно проверяет подключение и получает список топиков через Kafka API.
3. Бэкенд сопоставляет полученные топики с зарегистрированными источниками; обнаруженный топик без записи в БД отображается как доступный для добавления, но ещё не является источником приложения.
4. По явному действию пользователя топик регистрируется как выключенный источник без обязательного нормализатора.
5. Пользователь создаёт нормализатор и проверяет его на тестовом сыром сообщении.
6. Пользователь назначает нормализатор источнику.
7. Бэкенд разрешает активацию только при наличии корректного нормализатора, доступного подключения и существующего топика.
8. Бэкенд запускает или обновляет обработчик Kafka-источника и возвращает его наблюдаемое состояние.

Для внешнего источника пользователь задаёт подключение к OpenSearch-совместимому индексеру и выбирает одну из четырёх целей: конкретный индекс, семейство индексов по маске имени (например, `wazuh-states-inventory-*`), конкретный логический data stream либо семейство data streams по маске имени (например, `wazuh-findings-v5-*`). Маска индексов сопоставляется только с индексами, маска потоков — только с логическими именами потоков. OpenSearch index template не является источником документов. Wazuh 5 beta 5 использует data streams для семейств `wazuh-findings-v5-*`, поэтому обнаружение физических backing-индексов `.ds-*` не заменяет обнаружение логических имён потоков. Источник регистрируется в приложении отдельно от Kafka-источников. Его включение разрешает чтение через приложение после проверки конфигурации, но не запускает потребитель, не применяет нормализатор и не управляет индексером.

### 6.2. Поток данных

1. Обработчик читает сообщение и технические координаты Kafka: топик, партицию и offset.
2. Входной конверт валидируется; значение `log` передаётся выбранному нормализатору.
3. Нормализатор формирует ECS-событие и результат валидации.
4. PostgreSQL сохраняет сырой вход, нормализованное представление и происхождение события.
5. Kafka offset подтверждается только в согласованной связи с результатом обработки, чтобы перезапуск не приводил к неконтролируемой потере данных.
6. Повторная доставка распознаётся по координатам Kafka или иному согласованному идемпотентному ключу.
7. Ошибка попадает в контролируемый контур учёта ошибок с достаточным контекстом для диагностики; ошибочное сообщение не должно незаметно исчезать или навсегда блокировать источник.

Внешний путь выполняется только при пользовательском чтении: бэкенд проверяет права и настройки выбранного внешнего источника, преобразует типизированный запрос поиска или фильтрации в запрос индексера и возвращает найденные документы. Внешние события не копируются в локальные таблицы событий и не получают локальные Kafka-координаты.

Точная транзакционная стратегия, политика повторов и движение offset должны быть определены до реализации потребителя и закреплены в соответствующей задаче.

### 6.3. Логические компоненты

- **Kafka connection adapter** — проверка соединения и получение метаданных брокера.
- **Agent management** — регистрация Fluent Bit-агентов, закрепление топиков, управление индивидуальными Kafka-учётными данными и ACL, выдача конфигурации и восстановление после частичного сбоя.
- **Source configuration service** — управление источниками, их связями и состояниями.
- **Consumer supervisor** — запуск, остановка и восстановление обработчиков активных источников.
- **Input envelope validator** — проверка структуры входного сообщения.
- **Normalization engine** — расширяемый контракт нормализаторов и преобразование в ECS.
- **Normalization preview** — безопасная проверка профиля на примере без запуска потока.
- **Event storage** — атомарная запись события, происхождения и результата обработки.
- **Processing error storage** — учёт ошибок с безопасным диагностическим контекстом.
- **External connection adapter** — проверка доступа к OpenSearch-совместимому индексеру, выбор набора индексов и получение доступных полей и типов.
- **Event query service** — общий интерфейс чтения, поиска и фильтрации событий с отдельными реализациями для PostgreSQL и OpenSearch; сервер выбирает реализацию по типу источника.
- **FastAPI application** — API конфигурации, управления, статусов и данных.
- **React application** — пользовательские сценарии этапа и визуальное состояние конвейера.

Компоненты являются логическими границами. Они не требуют отдельных сервисов или процессов, если такое разделение не будет обосновано нагрузкой либо эксплуатационными требованиями.

## 7. Концептуальная модель данных

На этапе должны быть представлены как минимум следующие понятия:

- пользователь приложения, поддерживающий локальные и OIDC-реквизиты одновременно;
- роль с изменяемым названием и стабильным набором разрешений;
- сопоставление произвольной роли или группы из проверенного OIDC-токена с внутренней ролью;
- глобальная типизированная настройка приложения;
- подключение к Kafka и его несекретные параметры;
- агент Fluent Bit, его состояние и уникальное закрепление нескольких Kafka-топиков; действующий секрет агента не раскрывается повторно через API;
- источник событий с явным типом: Kafka-источник связан с конкретным топиком, внешний — с подключением и набором данных внешнего хранилища;
- подключение к внешнему хранилищу и параметры доступа, не раскрывающие секреты клиенту;
- нормализатор с JSONB-правилом и увеличиваемой целочисленной версией сущности;
- связь активного источника с применяемой конфигурацией обработки;
- сырое сообщение и время его сбора агентом;
- нормализованное ECS-событие;
- координаты Kafka и время приёма системой;
- состояние либо диагностическая информация обработчика;
- ошибка обработки и стадия, на которой она возникла.

В PostgreSQL хранятся конфигурация и состояние внешнего источника, но не прочитанные из него события. Понятия Kafka-координат, нормализатора и результата обработки относятся только к Kafka-источнику. Для внешнего события API сохраняет достаточную идентичность документа в пределах внешнего источника для открытия карточки без присвоения ему локальной идентичности `parsed_logs`.

Физические таблицы, связи, типы столбцов, использование JSONB, набор выделенных ECS-полей, индексы, партиционирование и политика хранения будут определяться отдельными задачами. Схема должна обеспечивать трассировку от ECS-события к исходному сообщению и источнику. Запись события сохраняет неизменяемые snapshot-имена подключения, источника и нормализатора, а также версию нормализатора, чтобы происхождение оставалось читаемым после удаления конфигурационных сущностей.

Для связей действует следующая политика удаления: `kafka_connection → sources типа Kafka` и `external_connection → sources типа external` используют `ON DELETE CASCADE`; удаление `source`, `normalizer`, `user`, `role` или иной конфигурационной сущности не должно каскадно удалять локально сохранённые события и использует `ON DELETE SET NULL` там, где зависимая запись сохраняет смысл. Удалённые ссылки компенсируются неизменяемыми данными происхождения в локальной записи события. Операции с конфигурацией внешнего источника не удаляют документы внешнего хранилища.

## 8. Требования к нормализации

- Выход соответствует выбранной и зафиксированной версии ECS.
- Один входной Kafka-конверт `{timestamp, log}` даёт не более одного нормализованного ECS-события: обработка применяется только к атомарной строке `log`; время `timestamp` отдельно означает сбор Fluent Bit.
- Одно правило нормализатора описывает несколько разновидностей событий одного источника как варианты с явным уникальным приоритетом. Выбирается первый подходящий вариант, и его неудача не маскируется переходом к следующему варианту.
- Внутри варианта допускаются последовательные и вложенные блоки разбора: JSON, пользовательские колонки, шаблоны и безопасные регулярные выражения. Блок может читать результат предыдущего блока; каждый режим может иметь несколько альтернатив. Поиск общей части между разными вариантами не является требованием.
- Сопоставление с ECS отделено от извлечения: один блок может извлечь много полей, а значение для ECS может происходить из извлечённого поля, совпавшего фрагмента или константы. Одно извлечённое поле внутри варианта сопоставляется не более чем с одним ECS-полем; объединение нескольких значений для одного ECS-поля задаётся явно и проверяется по типу.
- Обязательность задаётся пользователем для ECS-сопоставлений выбранного варианта. Когда все ожидаемые значения получены, результат `complete`; когда отсутствуют только необязательные — `partial` с причинами; когда отсутствует обязательное или не удаётся получить допустимое ECS-событие — `failed` с причиной.
- Системно добавляемый исходный текст и проверка непустого, типизированного ECS-результата не позволяют объявить произвольную строку успешной только потому, что пользователь не отметил обязательных полей.
- Время сбора Fluent Bit не подменяет время события, если последнее удалось извлечь из сырого лога; оба значения должны иметь однозначную семантику.
- Если полного времени события извлечь не удалось, время сбора Fluent Bit подставляется в `@timestamp` со статусом `partial` и причиной подстановки, кроме случая, когда пользователь явно отметил извлечение времени события из `log` как обязательное: тогда результат `failed` без подстановки.
- Источник, Kafka topic/partition/offset и применённая конфигурация нормализации трассируются.
- Нормализация детерминирована для одинакового входа и одинаковой версии конфигурации.
- Версия нормализатора увеличивается при каждом его изменении и записывается вместе с результатом обработки; восстановление старого правила на этом этапе не поддерживается.
- Пользователь может проверить конфигурацию на примере и увидеть результат либо структурированную ошибку до её активации.
- Полный и частичный результат сохраняются после введения механизма обработки, причём частичный содержит явную пометку и причины. Неуспешный разбор не сохраняется как якобы корректное ECS-событие, но исходный лог и ошибка не должны бесследно теряться.
- При первом запуске источника без подтверждённой позиции чтение начинается с самого раннего ещё доступного сообщения Kafka; при наличии позиции обработка продолжается с неё. Позиция чтения Fluent Bit на хосте независима от позиции потребителя приложения в Kafka. Если требуемая позиция стала недоступна из-за retention, система надёжно сохраняет операционное событие с диапазоном недоступных offset и автоматически продолжает с самого раннего доступного; пропуск не может быть молчаливым. Разность offset не выдаётся за точное число утраченных логов.
- Повторную доставку одной Kafka-записи отличают по идентичности подключения, Kafka topic ID, партиции и offset, а не по имени топика или хэшу содержимого лога: одинаковый текст и повторяющиеся offset у разных поколений топика допустимы. Нормализованные события и неуспешные сообщения учитываются идемпотентно. Пересозданный под прежним именем топик — новый источник: прежний источник сохраняется в архивном, выключенном состоянии, а новый регистрируется только по явному действию администратора.
- `failed` и неверный входной конверт после надёжного сохранения сырого сообщения и безопасной диагностики не блокируют дальнейший поток. При невозможности надёжной записи в PostgreSQL Kafka offset не подтверждается, обработка временно приостанавливается до восстановления. Автоматической повторной обработки уже учтённых ошибок и пересчёта старых событий при изменении нормализатора в этом этапе нет.
- В TASK-6 бэкенд реализует проверку и исполнение JSON-правил, preview и описание блоков для будущего конструктора; визуальный конструктор, Kafka-consumer и запись результатов в PostgreSQL выполняются последующими задачами.
- Механизм допускает последующее добавление новых форматов без изменения ядра всего конвейера.

Этап обязан поддержать не абстрактный пример, а минимум один согласованный реальный формат логов. Конкретный формат и способ задания правил будут выбраны перед задачей на нормализацию.

## 9. Требования к PostgreSQL

- База инициализируется с нуля через миграции.
- Все изменения схемы воспроизводимы и версионируются.
- Сохранение предотвращает неконтролируемые дубликаты при повторной доставке Kafka-сообщения.
- Частые пользовательские запросы имеют обоснованные индексы.
- Сырые и нормализованные данные различимы и связаны.
- Секреты подключения к внешним системам не возвращаются через API и не попадают в логи.
- Архитектура хранения не должна мешать последующему построению агрегатов и ML-признаков, но такие агрегаты в этом этапе не реализуются.

## 10. Требования к FastAPI-бэкенду

Бэкенд должен предоставлять достаточные API и фоновые механизмы для:

- проверки и управления параметрами Kafka-подключения;
- получения списка топиков и необходимых метаданных;
- регистрации и управления агентами Fluent Bit, назначенными топиками, индивидуальным доступом Kafka и выдаваемой конфигурацией;
- управления источниками и профилями нормализации;
- предварительной проверки нормализации;
- активации, остановки и просмотра состояния обработки;
- постраничного получения событий с согласованным минимальным набором фильтров;
- просмотра одного события, сырого входа и результата нормализации;
- удаления одного события, событий за заданный период либо всех событий выбранного источника с явным административным разрешением;
- просмотра ошибок обработки;
- проверки состояния самого приложения и его зависимостей;
- управления внешними подключениями и источниками, проверки соединения и получения доступных индексов и полей;
- чтения внешних событий через адаптер хранилища с серверным поиском и фильтрацией;
- предоставления одного типизированного контракта чтения событий выбранного источника поверх реализаций PostgreSQL и OpenSearch.

Контракты API должны быть типизированы, валидироваться и иметь единообразные ошибки. Фоновое потребление Kafka не должно зависеть от существования открытого HTTP-запроса. Контракт поиска и фильтрации не принимает произвольный SQL или OpenSearch Query DSL от клиента: реализации строят запросы к своим хранилищам после проверки полей, типов, операторов и прав доступа. Общий интерфейс гарантирует согласованное базовое поведение, но не скрывает неподдерживаемую конкретным хранилищем операцию под другим смыслом. Каталог локальных полей основывается на ECS `9.4.0`, каталог внешних — на схеме выбранного хранилища; внешние документы не отвергаются только из-за отличия версии ECS или наличия дополнительных полей.

Согласованная матрица операций прикладного API:

- `users`: CRUD, активация и деактивация, смена роли;
- `roles`: список, получение одной роли и переименование; создание третьей роли и удаление двух системных ролей запрещены;
- `oidc_role_mappings`: CRUD;
- `app_settings`: чтение и изменение только зарегистрированных настроек;
- `normalizers`: CRUD с обязательной проверкой переданной клиентом `version` при изменении;
- `kafka_connections`: CRUD, проверка подключения и получение списка топиков;
- `agents`: регистрация, чтение состояния и назначенных топиков, изменение назначения, отзыв и перевыпуск доступа; конкретный контракт и безопасная выдача конфигурации определяются задачей управления агентами;
- `sources`: CRUD, включение и выключение; назначение нормализатора относится только к Kafka-источнику;
- `external_connections`: управление конфигурацией, проверка подключения и обнаружение наборов данных для OpenSearch-совместимого индексера;
- `parsed_logs`: список, получение одной записи и административное удаление одной записи, записей за период либо всех записей источника.

Удаление событий остаётся операцией только для локальных `parsed_logs`; внешний источник предоставляет чтение без записи или удаления документов в индексере. HTTP-контракт таблицы и карточки событий должен указывать происхождение результата и корректно работать с идентичностью внешнего документа, не требуя для него локального UUID события.

Гость является аутентифицированным read-only пользователем и не может выполнять изменяющие операции. Администратору доступен полный согласованный функционал. Проверки выполняются по стабильным permissions роли, а не по её изменяемому отображаемому имени.

## 11. Требования к React-фронтенду

Обычные создание/редактирование, назначение нормализатора, включение и проверка соединения не требуют второй модалки, если постановка не определяет конкретное изменение как критическое. В свёрнутом меню — разделители групп и подсказки страниц. Полная, свёрнутая и мобильная навигация используют единую конфигурацию. Корпоративное оформление отложено за пределы этапа 1.

Согласованные требования к оформлению и взаимодействию:

- Ant Design — единственная библиотека UI-компонентов; React/TypeScript и MobX обязательны. Библиотеки маршрутизации, тестирования и сборки не являются дополнительными UI-библиотеками;
- три режима темы: светлый, тёмный и системный. Светлая схема основана на белом, тёмная — на тёмно-сером; акцент обеих `#64F86A`. По умолчанию используется системный режим, ручной выбор сохраняется в браузере; системный режим реагирует на изменения ОС;
- резиновая вёрстка от 320 до 2560 CSS px без горизонтальной прокрутки всей страницы. Для будущих широких таблиц допустима внутренняя горизонтальная прокрутка;
- layout без общего футера и сплошной панели хедера: локальный логотип в левом меню, название страницы сверху по центру рабочей области, аккаунт справа и основная область для страниц;
- на больших экранах меню сворачивается до иконок; на мобильных закрытое меню полностью скрыто и открывается выдвижной панелью с названиями разделов;
- матовое стекло с реально различимым размытием фона и акцентный контур — для меню, аккаунта и вспомогательных окон, без отдельной стеклянной панели хедера. Обязательны читаемость, непрозрачный fallback и учёт пользовательских предпочтений уменьшения движения; таблицы не должны терять чёткость из-за эффектов;
- клавиатурное управление: Tab/Shift+Tab, заметный фокус, Enter/Space, Escape, управление фокусом при открытии и закрытии окон и мобильного меню; действия не должны требовать hover, мыши или перетаскивания;
- настройки текущего аккаунта на этапе включают сведения о пользователе, выбор темы и выход. Самостоятельное редактирование профиля, смена пароля и загрузка логотипа не входят в согласованный объём фронтенда;
- интерфейс и инструкции на русском языке; технические имена ECS/WCS, идентификаторы и имена полей сохраняются;
- браузер использует относительный `/api/v1` через общий reverse proxy. Секреты подключения и OIDC не попадают во frontend bundle, browser storage или журналы;
- доступные действия определяются permissions из серверной сессии, а не названием роли. Сессионный токен хранится только в HttpOnly cookie; CSRF передаётся для всех соответствующих небезопасных HTTP-методов, включая POST-поиск;
- публичный минимальный метод доступных способов входа вводится в TASK-14, чтобы UI не угадывал состояние OIDC. Он возвращает только признаки доступности локального и OIDC-входа.

Минимально необходимые пользовательские разделы:

1. **Обзор** — состояние зависимостей и активных источников, последние ошибки.
2. **Подключения** — настройка и проверка Kafka с просмотром топиков; настройка и проверка OpenSearch-совместимого индексера с выбором набора индексов.
3. **Источники** — создание, редактирование, активация и остановка Kafka-источников и внешних источников с различением их допустимых настроек.
4. **Нормализация** — управление профилями и предварительный просмотр результата на тестовом сообщении.
5. **События** — пользователь выбирает один источник и работает с таблицей его событий, серверным поиском и фильтрами. Строка раскрывается в карточку с полями события. Для локального события доступны сырой вход, ECS-представление и статус нормализации; для внешнего — документ и поля, предоставленные выбранным хранилищем. Агрегатных графиков на этом этапе нет.
6. **Ошибки обработки** — список ошибок со стадией, источником и безопасной диагностикой.
7. **Агенты** — регистрация и управление Fluent Bit-агентами, закрепление топиков и выдача готовой конфигурации; доступно администратору.

Информационная архитектура страниц может быть упрощена или объединена в ходе проектирования интерфейса, если все пользовательские сценарии сохраняются.

## 12. Надёжность, безопасность и наблюдаемость

- Параметры и секреты валидируются; секретные значения маскируются в API, UI и логах.
- У каждого агента отдельный Kafka principal и доступ только к назначенным топикам. Секрет выдаётся при создании или перевыпуске, не возвращается при обычном чтении. Файл конфигурации с ним считается секретным, доставляется администратору через HTTPS и требует ограниченных прав на хосте агента.
- Доступ к внешнему индексеру осуществляется только через бэкенд с минимально необходимыми правами чтения; отключение или удаление внешнего источника в приложении не изменяет и не удаляет данные в индексере.
- Внешнее подключение использует учётную запись индексера по HTTPS с проверкой сертификата сервера и имени хоста. Общедоверенные CA используются без загрузки; администратор может предоставить публичный корпоративный CA для конкретного подключения. Загруженный CA не расширяет глобальное доверие бэкенда. Приватные ключи, клиентские сертификаты, mTLS и отключение проверки TLS в продакшене не входят в этап; пароль не раскрывается в API и логах.
- Запросы к внешнему хранилищу ограничены выбранным источником, правами пользователя, допустимыми полями и операторами, временем выполнения и объёмом ответа; конкретные пределы определяются в задаче адаптера.
- Ошибки одного источника не должны без необходимости останавливать остальные источники.
- После перезапуска приложение восстанавливает обработку активных источников контролируемым способом.
- Завершение приложения корректно останавливает потребителей и не подтверждает необработанные сообщения.
- Значимые действия и ошибки имеют структурированные логи с идентификаторами источника и события, но без утечки секретов.
- Есть health/readiness-проверки приложения, PostgreSQL и Kafka с корректным различением их назначения.
- Ошибки API не раскрывают внутренние трассировки пользователю.
- Конфигурация окружения отделена от исходного кода.
- В production наружу публикуются только HTTPS-вход веб-приложения и необходимый внешний Kafka-listener `SASL_SSL`; PostgreSQL, FastAPI, внутренние и controller-listeners Kafka недоступны напрямую извне. Внешний listener проверяет персональную учётную запись агента и ACL; его доступ дополнительно ограничивается сетевой политикой. Внутренние клиенты приложения используют отдельные защищённые учётные записи. Пароли и ключи не имеют учебных значений и не встраиваются в образы.
- В development не отключаются управление агентами, SCRAM и ACL. `SASL_PLAINTEXT` допустим только для локального loopback-стенда с синтетическими данными и тестовыми секретами; удалённый стенд и реальные агенты используют `SASL_SSL`. Различие транспорта не создаёт отдельный UI или API.
- Swagger UI и схема OpenAPI доступны для разработки и тестов, но не публикуются в production. За доверенным proxy бэкенд корректно использует исходные host и HTTPS-схему, не доверяя произвольным forwarded-заголовкам извне.

## 13. Проверки качества

Набор проверок должен включать соразмерное покрытие следующих уровней:

- модульные тесты валидации входного конверта и нормализации;
- тесты идемпотентности и поведения при ошибках;
- тесты моделей, миграций и ключевых запросов PostgreSQL;
- тесты контрактов FastAPI;
- тесты общего контракта чтения и фильтрации для PostgreSQL и OpenSearch, включая различия каталогов полей, обработку недоступности внешнего хранилища и запрет изменяющих операций;
- тесты MobX-логики и критических пользовательских компонентов;
- интеграционный тест цепочки Kafka → обработчик → PostgreSQL;
- отрицательные проверки персональной аутентификации и ACL: неизвестный агент, неверный пароль и запись в чужой топик отклоняются; отзыв и перевыпуск доступа проверяются отдельно;
- сквозная проверка основного сценария через UI или максимально близкий автоматизированный эквивалент.

Конкретный баланс тестов определяется в задачах. Критическая цепочка не может считаться принятой только на основании ручной демонстрации.

## 14. Критерии завершения этапа

Этап считается завершённым, когда в чистой поддерживаемой среде можно воспроизвести следующий сценарий:

1. Запустить PostgreSQL, Kafka, бэкенд и фронтенд по документации.
2. Автоматически применить миграции к пустой базе.
3. Через UI зарегистрировать агента, назначить ему топик, получить конфигурацию и проверить его аутентифицированную отправку; неизвестный агент и запись в чужой топик должны отклоняться.
4. Через UI настроить и успешно проверить подключение к Kafka; зарегистрированный агентом топик виден как выключенный источник.
5. Создать конфигурацию нормализации, проверить её на реальном примере и активировать источник.
6. Отправить корректное сообщение согласованного формата в Kafka.
7. Убедиться, что сообщение преобразовано в валидное ECS-событие и сохранено с сырьём и происхождением.
8. Найти событие в интерфейсе и просмотреть исходное и нормализованное представления.
9. Отправить некорректное сообщение и увидеть контролируемую ошибку без незаметной потери и без остановки всей системы.
10. Перезапустить бэкенд и убедиться, что активная обработка восстанавливается без неконтролируемого дублирования уже сохранённых событий.
11. Через UI настроить OpenSearch-совместимое подключение и зарегистрировать внешний ECS-ориентированный источник, включая проверку на совместимом с Wazuh 5 наборе данных.
12. Выбрать внешний источник, найти и отфильтровать его документы в таблице и раскрыть карточку; подтвердить, что документы не копировались в `parsed_logs` и не проходили через Kafka-конвейер.
13. Переключаться между локальным и внешним источником, сохраняя единый пользовательский сценарий таблицы, поиска, фильтрации и карточки при корректном различении доступных полей и операций.
14. Выполнить согласованный набор автоматических тестов без ошибок.

Дополнительно должны отсутствовать незадокументированные ручные действия, необходимые для основного сценария, и критические дефекты, препятствующие дальнейшему развитию проекта.

## 15. Предварительные направления декомпозиции

Это предварительный трек, а не готовые постановки или разрешение на реализацию. Каждая следующая задача формируется поочерёдно после приёмки предыдущей; объём и границы уточняются при её обсуждении.

- TASK-1–7: модель данных, аутентификация и прикладное API, Kafka-подключения и источники, чтение локальных событий и каталог ECS, движок нормализации, надёжное хранение результатов обработки.
- TASK-8: Kafka consumer и жизненный цикл обработчиков, восстановление позиции и подтверждение offset после надёжного сохранения; согласованное дополнение FIX-TASK-8-4 вводит явный учёт retention-разрывов и разделение поколений топиков без автоматического создания нового источника.
- TASK-9: операционный API для состояния обработчиков, сохранённых ошибок и диагностики, необходимой обзорной странице; без аналитических агрегатов.
- TASK-10: различение Kafka- и внешних источников, конфигурация внешних подключений с защищённым исходящим HTTPS и необязательной загрузкой CA, проверка доступа и выбор индекса, семейства индексов по маске, data stream либо семейства data streams по маске OpenSearch-совместимого индексера. Поддержка data streams добавлена после живой проверки Wazuh 5 beta 5 отдельным исправлением к TASK-10.
- TASK-11: общий сервисный интерфейс чтения и поиска событий, реализация для PostgreSQL с сохранением действующих контрактов локальных событий.
- TASK-12: реализация этого интерфейса для OpenSearch, обнаружение полей и проверка на ECS-ориентированных документах, включая Wazuh 5; без локального копирования и агрегатов.
- TASK-13: основа development/production-поставки существующих компонентов: Compose, HTTPS reverse proxy, production TLS для внешнего Kafka-канала без SASL/ACL, dev-only Swagger/OpenAPI и корневая документация. Подготовить единую точку входа для будущего React, но не создавать его заранее.
- TASK-14: каркас React/TypeScript/MobX/Ant Design, темы, адаптивный layout, клавиатурная доступность, маршруты, локальный/OIDC-вход, сессия и API-клиент; минимальный API доступных способов входа и подключение dev-сервера через proxy. Предметные страницы пока не реализуются.
- TASK-15: страницы `/connections` и `/sources` с категориями «Собственные подключения» (Kafka) и «Внешние подключения» (индексеры). Источники создаются только на `/sources`; `/connections` показывает discovery и связи с существующими sources. Одна цель на source, повторная одинаковая цель в подключении запрещена; external поддерживает index/index_pattern/data_stream/data_stream_pattern. Назначение готового normalizer и enable/disable Kafka здесь, создание normalizer — TASK-16. Существующие permissions/контракты сохраняются: external live discovery/test требуют connections.write. Изменение external connection/CA выключает связанные sources и объясняется пользователю. Backend/migrations не расширяются без нового согласования; UX подчинён постоянным принципам AGENTS.md, раздел 10.
- TASK-16: список и редактор нормализаторов: компактная древовидная схема блоков со связями по названиям полей и настройками в модальных окнах, редактируемый JSON того же правила, выбор полей ECS, встроенные шаблоны Nginx combined/IIS W3C/syslog/JSON, копирование существующего нормализатора, импорт/экспорт и промпт для внешней нейросети. Для preview пользователь вводит только строку `log`; требуемое контрактом `{timestamp, log}` служебное время автоматически подставляет frontend. Нормализатор разбирает только `log`. Получение сырых сообщений из Kafka не входит.
- TASK-17: безопасный отладочный просмотр настоящих сырых сообщений зарегистрированного Kafka-источника без влияния на рабочий consumer и его offset. В редакторе нормализатора остаётся ручной ввод `log`; для режима источника загружается неизменяемый снимок до 50 последних доступных Kafka-записей с явным обновлением. Фиксированный режим проверяет выбранную запись, авто-режим последовательно проверяет записи снимка с шагом пять секунд, допускает паузу/остановку и завершается на конце снимка. Результаты и ошибки доступны только в текущем сеансе, безопасный отчёт можно скачать. Потерю накопленных результатов подтверждает пользователь; новых сообщений авто-режим не ожидает.
- TASK-18: таблица одного выбранного источника, скользящая неделя по умолчанию, серверные поиск и фильтрация, курсорная пагинация и раскрываемая карточка локального или внешнего события; административное удаление только локальных логов с подтверждением; без агрегатных графиков. Задача принята; косметические пожелания, не относящиеся к её критериям приёмки, отложены до финальной шлифовки.
- TASK-19: основа защищённой Kafka в development и production: SCRAM-аутентификация, ACL и отдельные служебные полномочия внутренних клиентов; для строго локального dev допустим `SASL_PLAINTEXT`, для production и удалённых стендов обязателен `SASL_SSL`. Инфраструктурные и отрицательные проверки выполняются до создания пользовательского менеджмента агентов.
- TASK-20: backend-модель и API жизненного цикла агентов: персональные учётные данные, уникальное закрепление нескольких топиков за агентом, создание новых или присоединение незакреплённых существующих топиков, ACL, отзыв/перевыпуск доступа и восстановление после частичных сбоев Kafka/PostgreSQL. Соответствующие новые источники регистрируются выключенными. Публичный API остаётся частью бэкенда; административные операции Kafka выполняет закрытый служебный процесс того же бэкенда без внешнего адреса, чтобы обычный API-процесс не получал Kafka admin secret. При снятии топика или отзыве агента запись для него прекращается, но уже включённые источники продолжают дочитывать накопленное; топики, источники и события не удаляются. Перевыпуск доступа без переходного периода немедленно отзывает старые учётные данные после выполнения операции в Kafka и требует явного предупреждения о возможной паузе агента.
- TASK-21: страница «Агенты» с тем же API в development и production: регистрация, назначение топиков, безопасная одноразовая выдача готовой конфигурации Fluent Bit и управление доступом. Сквозная проверка «агент → Kafka → нормализация → PostgreSQL → таблица событий» без ручной настройки учётной записи и ACL Kafka.
- TASK-22: доработка конфигурации агента: выбор входа Fluent Bit отдельно для каждого назначенного топика (`tail`, `winevtlog`, `systemd` или общий шаблон для другого входа), понятные placeholders и получение строкового `log` в конверте `{timestamp, log}`. Для `systemd` допустим фиксированный встроенный Lua-код внутри единственного генерируемого конфига: исходное время записи `journald` сохраняется в `log`, а timestamp конверта обозначает обработку агентом; отдельный файл или новая зависимость агенту не поставляется. Администратор может повторно просматривать и скачивать сгенерированный шаблон без пароля; действующий секрет остаётся одноразовым, при его утрате требуется явный перевыпуск. Шаблон не выдаётся за фактически запущенный конфиг на хосте агента.
- TASK-23: страница «Диагностика» собственного конвейера `агент → Kafka → источник/обработчик → нормализатор → PostgreSQL`. Мнемосхема помогает понять связи и локализовать ошибку; состояния и причины, сохранённые ошибки обработки и события Kafka ведут к деталям и страницам управления, но действия изменения выполняются только в своих разделах. Внешние ECS-источники не проходят этот конвейер и не включаются в его схему. Отсутствие телеметрии агента не изображается как его исправная работа; текущее состояние обработчика отличается от исторических ошибок.
- TASK-24: страница «Главная» как краткий модульный обзор приложения в целом. Общая структура адаптируется к permissions пользователя; блоки обработки данных и анализа ведут в доступные специализированные разделы, в том числе диагностику собственного конвейера. Допустим минимальный read-only агрегирующий API для точных и дешёвых инвентарных показателей без полного сканирования событий. Наглядные диаграммы разрешены для подтверждённых распределений текущего снимка с текстовыми значениями и временем обновления; временные ряды, активность агентов, аномалии и иная ещё не реализованная аналитика не имитируются. Обзор будет расширяться в последующих этапах.
- TASK-25: страница «Администрирование» на существующем API пользователей, двух системных ролей и сопоставлений ролей OIDC. Компоновка — последовательные вертикальные блоки при любой ширине; внутри блока «Роли и доступ» роли и OIDC-сопоставления переключаются локальной навигацией без скачков интерфейса. Гость не имеет доступа ни к странице, ни к API чтения пользователей, ролей и OIDC-сопоставлений: его право `users.read` отзывается на сервере с миграцией существующих БД. Создание произвольных ролей и изменение набора разрешений не входят в задачу; достаточность двух ролей оценивается после работы со страницей.
- TASK-26: включить production-сборку React в поставку Compose и обслуживание статических файлов через существующий HTTPS reverse proxy; проверить реальные маршруты, локальный вход и сессию в браузере через production proxy, сохранив development-профиль. С приёмки задачи production smoke включает frontend-маршрут. Не менять управление OIDC и внешний вид приложения в этой задаче.
- TASK-27: безопасное управление одним OIDC-провайдером через новый блок «Способы входа» существующей страницы «Администрирование» с проверкой в development на loopback и в production через HTTPS. Client secret принимается администраторским интерфейсом и хранится в БД только зашифрованным существующим ключом из защищённого файла хоста; API не возвращает секрет. Публичный корпоративный CA при необходимости загружается через интерфейс и расширяет доверие только для этого провайдера. Настройки сначала сохраняются как черновик, проходят проверку discovery/TLS и пробный OIDC-вход, после чего включаются без рестарта; ошибка не заменяет прежнюю рабочую конфигурацию. Локальный вход нельзя отключить через UI, он остаётся резервным. Роли и OIDC-сопоставления остаются в существующем блоке. Отдельная страница и маршрут `/settings` полностью удаляются; административное API настроек недоступно гостю. Блоки «Администрирования» и действия внутри них показываются по фактическим правам, а не только по названию роли; при нынешних двух ролях страницу видит лишь администратор. Инфраструктурные ключи и секреты остаются в защищённых файлах хоста; открытые секреты в БД запрещены.
- TASK-28: финальная визуальная шлифовка принятого фронтенда. Исполнитель самостоятельно находит и исправляет заметные дефекты адаптива, отступов, переполнения, читаемости, состояния фокуса и визуальной согласованности всех принятых страниц. На странице «События» фильтры и карточка события открываются поверх таблицы, большие текстовые значения исходно свёрнуты; повторный заголовок страницы в контенте убирается, если он уже есть в общем хедере. Изменения ограничены фронтендом и представлением; API, права, данные и предметные сценарии остаются прежними. Работа ограничена одним систематическим обзором страниц и проверкой исправлений; новые продуктовые возможности не добавляются.
- TASK-29: завершающая приёмка этапа: полная переработка пользовательской документации запуска и эксплуатации в краткое, навигационное и проверенное руководство с командами, удобными для копирования; полный регрессионный прогон и сквозная проверка обоих путей событий, включая управляемых агентов и React через production HTTPS proxy.
- Настраиваемое корпоративное оформление (название приложения, акцентный цвет, логотип) отложено за пределы этапа 1; его отдельная постановка потребует согласования хранения, формата логотипа и контраста обеих тем. Параметры и секреты внешних подключений остаются в «Подключениях».

## 16. Открытые решения перед декомпозицией задач

Следующие вопросы необходимо решить по мере обсуждения задач; исполнитель не должен выбирать ответы самостоятельно:

1. TASK-19: порядок безопасного включения SCRAM и ACL на уже работающем брокере без потери накопленных топиков/offset, конкретные служебные Kafka-principal и права, TLS-доверие внутреннего клиента, конфигурация изолированных dev и production listener; недопустимо оставлять доступный неаутентифицированный путь в production.
2. TASK-20: определить в постановке и проверить схемы состояний и восстановления частичного provisioning, правило присоединения существующего топика и проверки его поколения. Согласованы закрытый provisioning-процесс в составе бэкенда, сохранение состояния источников и накопленных данных при снятии топика/отзыве агента, немедленный отзыв старых учётных данных при перевыпуске без переходного периода. Не считать операции Kafka и PostgreSQL одной транзакцией и не удалять накопленные топики автоматически.
3. TASK-21: граница одноразовой выдачи и скачивания конфигурации с секретом, описание входов Fluent Bit для нескольких служб/топиков без хранения секретов в браузере, проверка установки агентом на отдельном хосте.
4. TASK-26: production-сборка React обслуживается действующим HTTPS proxy без dev-сервера и runtime-секретов в bundle; для завершающей задачи остаются права файлов на целевом Linux-хосте и итоговая матрица сквозной приёмки.
5. TASK-27: граница секретов OIDC, корпоративное CA-доверие, безопасное обновление runtime-конфигурации и пробный вход без утраты доступа администратора согласованы выше. Детали протокола пробного входа и переключения конфигурации задаются в TASK-27 и проверяются тестами.
6. Для отложенной задачи корпоративного оформления определить допустимый формат логотипа и правила контраста выбранного акцентного цвета в обеих темах перед её постановкой в будущем этапе.
7. Дополнительная политика автоматического удаления сырых событий и ошибок, целевые объёмы и задержки требуют отдельного согласования; исполнитель не вводит автоматический retention самостоятельно.

Решения по RE2 и JSON-правилам, идемпотентности Kafka, ошибкам и восстановлению позиции, HTTPS/CA и шифрованию внешних секретов, общему контракту фильтров и Wazuh 5 beta 5 уже приняты в TASK-6–13 и не являются открытыми вопросами. Источник истины для реализованных контрактов — соответствующие схемы, сервисы, тесты и документация. Автоматическая привязка локальной и OIDC-идентичности по email запрещена; отдельный пользовательский сценарий привязки не добавляется без согласования. Первичный администратор создаётся существующей CLI-командой.

Решения, влияющие на будущие задачи, после согласования вносятся в этот план до постановки соответствующей задачи.

### Ограничения и вопросы для Главного архитектора

- Сквозная проверка Wazuh использовала настоящий совместимый индексер с синтетическими документами, без Wazuh Manager. Отдельный физический хост агента и живой Windows Event Log в постоянном профиле не проверялись; локальная пользовательская проверка доставки Windows-логов была, но не заменяет воспроизводимый тест отдельного хоста.
- Производительность при большом числе пишущих служб, длительная работа под нагрузкой, горизонтальное масштабирование и высокая доступность не проверялись и не обещаются результатом этапа 1. Политика автоматического retention для локальных событий и ошибок остаётся несогласованной.
- Корпоративное оформление, ML, LLM, агрегаты, аномалии, уведомления и расследования оставлены за границами этапа. Дорожная карта не назначает следующий этап до решения человека с Главным архитектором.
- При передаче этого итога в рабочем дереве находились незакоммиченные изменения `.gitignore` и `docs/frontend-pages-and-style.md`, сделанные вне подготовки итога. Этапный архитектор их не изменял; Главному архитектору следует отличать их от зафиксированного коммитом результата этапа.

Главному архитектору требуется проверить соответствие цели, границ и всех 14 критериев разделов 3, 5 и 14 фактическому результату, а также пригодность двух путей событий как основы следующего этапа. Если появятся замечания, они оформляются отдельным ревью этапа без молчаливого расширения его границ.
